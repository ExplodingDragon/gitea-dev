原 PR 提交哈希保持不变，Git 可以在下一轮从各自当前头计算增量。数据库普通提交位于两个合并之后，清楚表达 self 相对正常业务合并结果的维护差异。

实现验收点

  • 23ca84e0c8、d87314faab 各有两个父提交。
  • f19882d9ba、8d65b612a2 各有一个父提交。
  • 当前 self 头为 8d65b612a2，并能沿第一父回到上一版 53d76a7ab0。

四项提交的职责

提交类型职责
23ca84e0c82c43f8c457d3736a4ab721b6525c93双父合并接入 Codespace PR 当前头和最新上游，组合现有 Pages 行为

拆成四笔记录是为了让代码来源、文件身份和数据库执行安排可以分别审阅。任何一项出现问题时，都能定位到具体来源与处理阶段，不需要改写已有提交。

实现验收点

  • 两个合并提交的第二父分别精确等于固定 PR 头。
  • 文件身份提交不改变任何迁移实现内容。
  • 最后一项提交的范围为迁移列表和 self 升级测试。

固定来源与祖先关系

本轮固定来源为：

  • upstream/main@23836eb610b6673dc4ef7001d432e48dd3af1537；
  • Codespace PR #38337 0f1c19ba10e2d6e026efd0f63e435e545fc3d230；
  • Pages PR #40071 5000d55fb2b0c3312fe4a49e3716bd871efc1ce7。

两个 PR 头都包含同一个上游提交，因此不另建一笔重复的上游合并。分别保留两个 PR 合并，是为了让下一轮仍能独立追踪 Codespace 和 Pages 的提交增量。

实现验收点

  • 三次 git merge-base --is-ancestor <来源> self 都返回成功。
  • 两个 PR 头的共同上游为 23836eb610。
  • 下一轮分别以 0f1c19ba10、5000d55fb2 为 PR 增量起点。

后续历史组织

下一轮继续为每个发生更新的 PR 创建双父合并提交，并在所有业务合并完成后单独提交 self 数据库安排。普通上游代码由 PR 带入；如果将来 PR 不再包含目标上游，再根据真实祖先关系增加明确的上游合并。

这种历史结构优先保存事实：来源提交保持原哈希，人工冲突解决位于对应合并，self 特有迁移位于后续普通提交。外层仓库只在内层推送成功后更新子模块指针。

实现验收点

  • 新 PR 头通过合并第二父进入 self。
  • self 数据库提交的范围为迁移列表、迁移实现和迁移测试。
  • 外层提交所指向的内层提交已经存在于 origin/self。
