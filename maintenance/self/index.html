Gitea self 分支维护总览

维护目标

self 是本项目直接部署和持续升级的 Gitea 分支。内层仓库使用 gitea/self 保存代码与数据库迁移，外层仓库使用 gitea-dev/main 固定已验证的内层提交并保存维护记录。

非数据库代码按普通方式合并 Codespace PR #38337、Pages PR #40071 和它们包含的上游更新，保留两个 PR 的原始提交以及双父合并记录。数据库迁移采用 self 自己的连续编号，因为迁移 365 之后，self、上游和两个 PR 已经对相同版本号赋予不同结构含义。当前 self 头为 53d76a7ab066085c21af9098862392ba1d2fc420，期望数据库版本为 372。

实现验收点

  • 内层当前分支为 self，外层当前分支为 main。
  • upstream/main@c74f2f9216、Codespace PR 头 68bcefaa69 和 Pages PR 头 e645501a81 都是当前 self 的祖先。
  • modelmigration.ExpectedDBVersion() 对当前代码返回 372。

数据库升级关系

self 已发布的迁移 365—367 依次建立 Codespace、Pages 和 Codespace Manager 注册令牌结构。本轮在末尾追加迁移 368—371：

昨天版本为 368 的 self 实例会顺序执行 368、369、370、371，因此可以直接升级到今天的版本 372。全新安装、分叉前数据库以及更早的 self 数据库也会沿同一序列升级。

迁移 365 之后建立的上游数据库或单独 PR 数据库使用了另一套编号含义，它们继续沿各自分支升级。这个边界让 self 只维护一条可验证的原生迁移序列，也避免根据表结构猜测数据库来源。

实现验收点

  • 版本 368 的 self 数据库有且只有四项待执行迁移，完成后版本为 372。
  • 数据库版本不高于 365 的分叉前实例会执行 self 尚未完成的全部迁移。
  • 运维记录能区分数据库来自 self，还是来自迁移 365 之后的上游或单独 PR。

迁移文件命名

来源迁移文件使用以下格式：

pr-<来源 PR>-v<来源迁移编号>-patch<同一来源迁移的增量序号>.go

文件名固定描述变化来自哪里，不跟随它在 self 中的实际执行位置变化。例如 pr-38337-v365-patch3.go 表示 Codespace PR #38337 对其来源迁移 365 的第三项数据库变化，它在当前 self 中实际注册为迁移 371。实际执行编号统一记录在 migrations.go、迁移映射和逐项说明中。

这样设计后，后续上游移动迁移编号或再次合并 PR 时，维护文件仍能按来源稳定识别，Git 重命名也不会掩盖真实的迁移内容变化。

实现验收点

  • 所有来源化文件名都能指出来源 PR、来源迁移编号和增量序号。
  • 文件名中的来源编号与 self 实际编号分别记录，不混用含义。
  • 同一 PR、同一来源迁移的 patchN 按进入 self 的变化顺序递增。
