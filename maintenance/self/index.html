Gitea self 分支维护总览

self 是本项目直接维护的 Gitea 分支。它从上游提交 d3021b69eec62d40752f7034ced4dd091fe085af 建立，以完整 Git 历史合并 Codespace PR #38337 和 Pages PR #40071，并在 Gitea 原生数据库迁移序列中依次安排两项迁移。

这个分支的目标是让两个仍各自占用上游迁移 365 的 PR 可以同时运行。上游合并前无法为两个 PR 分配同一个迁移编号，因此 self 将 Codespace 保留为迁移 365，把 Pages 调整为迁移 366。数据库一旦执行这组迁移，就进入 self 的版本含义，后续继续沿 self 升级。

两个 PR 通过双父合并提交接入，因而原提交、作者、提交顺序和来源分支关系都可以从 self 追溯。迁移文件的命名和编号调整放在独立提交中，使审阅者可以把功能实现与 self 的数据库版本安排分开查看。

维护边界

self 使用 Gitea 现有的 version 表、modelmigration/migrations.go 和迁移执行流程。每次需要数据库变化时，维护者把函数追加到原生迁移列表末尾，并分配下一个连续编号。这样安装、启动检查、gitea migrate 和迁移测试继续走同一条成熟路径。

数据库来源以分支和备份记录为依据。当前支持从分叉前的较低上游版本升级，也支持从明确由 Codespace PR #38337 建立的数据库继续升级。Pages PR 单独建立的同号数据库和分叉后使用相同编号的上游数据库具有不同含义，应从进入这些分支前的备份转入 self。具体范围见数据库版本与升级范围。

文档入口

  • 数据库版本与升级范围解释迁移编号、数据库版本和可接受来源。
  • 迁移映射记录上游编号到 self 编号的对应关系。
  • Git 历史结构说明合并提交和数据库记录提交如何组织。
  • 上游同步流程给出以后合并上游和新增迁移的步骤。
  • 冲突解决记录解释本次五处冲突为何这样组合。
  • 验证记录列出已执行检查和已确认的上游环境差异。
  • patches/ 为每个来源 PR 保存逐项迁移记录。

实现验收点

  • Gitea 内层仓库存在本地 self 分支，头提交为 2fd1c04de5 或其后继提交。
  • PR #38337 的头提交 1c0f24e4fd 和 PR #40071 的头提交 534024baa2 都是 self 的祖先。
  • 两个 PR 分别通过双父合并提交进入 self，原提交没有被压缩或重新生成。
  • 数据库只使用 Gitea 原生迁移列表，Codespace 为迁移 365，Pages 为迁移 366。
  • 当前迁移序列的期望数据库版本为 367。
  • 维护文档可以从目录定位来源提交、迁移映射、冲突理由和验证结果。
