Gitea Pages 与 Codespace 设计文档

上游同步流程

一、固定同步输入

同步前获取 upstream/main、仍在维护的 PR 引用和 origin/self，为每个输入记录完整提交哈希。完整哈希使合并父提交、迁移映射和测试结果指向同一份代码，即使 PR 后续继续提交也不会改变本轮记录。

内层工作分支使用 self，起点是已经推送的 origin/self。同步前同时核对 modelmigration/migrations.go 的最后编号、迁移映射最后一行和文档中的期望数据库版本；三者一致后，后续差异才能明确归属于本轮来源更新。

实现验收点

  • 同步记录包含 upstream/main、相关 PR、origin/self 的完整哈希。
  • 内层当前分支为 self，同步起点可由 origin/self 复现。
  • 代码中的最后迁移、映射表和期望数据库版本表达同一序列。

二、合并上游与 PR 更新

每个来源通过双父合并进入 self。PR 头已经包含目标 upstream/main 时，先合并包含实际功能变化的 PR，由它同时带入上游；随后合并其他 PR 头补齐来源历史。文件树不变的合并仍被保留，因为第二父明确表示同步位置，并改善下一轮共同祖先计算。

自动合并结果先按业务行为审阅。普通文件保留来源 PR 的当前实现；两个 PR 修改同一行为时，组合双方可观察行为，并记录调用顺序、权限、事务和测试依据。生成文件使用仓库规定的生成入口更新。两个来源提出互斥业务语义时，以具体行为差异提交设计审阅，再形成合并提交。

实现验收点

  • 每个当前 PR 头都是 self 的祖先，并可作为对应合并提交的第二父定位。
  • PR 头包含目标上游时，目标上游也是最终 self 的祖先。
  • 文件树不变的来源更新仍有双父提交，且树对象与第一父相同。
  • 人工组合的业务行为在冲突记录中有原因、最终顺序和测试入口。

三、移植数据库变化

比较上次固定的 PR 头与本轮 PR 头之间的 modelmigration 差异，并按变化落点选择一种方式：

  1. 来源没有数据库差异时，保留现有 patch 和数据库版本，只更新“当前已同步 PR 头”。
  2. 来源增加尚未进入 self 的新迁移时，按来源相对顺序为它分配 self 末尾的连续编号。
  3. 来源修改已经进入 self 的旧迁移时，现有 patch 保持已发布结构，把新增表、列、索引或数据变换放进末尾新的 patchN。

第三种方式保证已经运行 self 的数据库会执行增量，也让低版本数据库按同一原生序列得到相同结构。新文件使用 pr-<来源 PR>-v<self 编号>-patch<序号>.go，并在迁移列表、映射、逐项文档、版本文档和验证记录中同步登记。

迁移记录使用独立普通提交。提交只包含迁移列表、迁移实现和直接测试，使来源业务代码与 self 的数据库安排可以分别审阅。

实现验收点

  • 新迁移从当前末尾连续编号，ExpectedDBVersion() 等于最后编号加一。
  • 已发布 patch 与其固定提交或上一已发布头内容一致。
  • 旧迁移的来源增量在新 patch 中可独立执行，并有幂等性与关键约束测试。
  • 迁移记录提交只包含 modelmigration 及直接测试。
  • 文件名、映射、逐项文档和实际注册编号一致。

四、代码质量与完整验证

先审阅来源更新是否已经清理被替代的入口、模板、前端组件和测试，再执行 make fmt、make tidy 和许可证生成检查。静态检查使用 make checks 与 make lint，构建使用 make build；测试使用 make test-migration、make test-backend、make test-frontend 和适用的集成测试目标。Gitea 测试统一由 Make 入口启动，以采用仓库维护的构建标签、超时和环境设置。

完整集成测试存在已确认的环境差异时，验证记录写明测试名、实际值、期望值、工具版本和与本轮代码的关系。Playwright 端到端测试需要浏览器及系统动态库，环境具备后直接运行标准 Make 目标。维护文档使用 mdBook 构建验证链接和结构。

实现验收点

  • 格式化、依赖、许可证、静态检查、构建、迁移、后端和前端测试都有实际结果。
  • 功能相关集成测试在完整集成套件或定向 Make 目标中运行。
  • 环境相关失败记录具体断言和工具版本，其他测试继续运行到套件结束。
  • 文档可以由当前仓库的 mdBook 配置完整构建。

五、固定外层仓库并推送

验证完成后，先在内层 self 提交所有计划内代码并确认工作树干净。外层 main 只暂存内层 Gitea 提交指针和 src/maintenance/self/ 文档；外层其他在制功能改动保持原状态。推送前重新获取远端并确认没有远端前进，然后先推内层 self，验证远端哈希，再推外层 main。

这个顺序保证外层提交引用的内层对象已经可从远端取得，同时维持外层 main 作为部署和维护文档入口、内层 self 作为 Gitea 实现分支的职责划分。

实现验收点

  • 内层维护提交已推送到 origin/self，远端哈希等于本地 self。
  • 外层维护提交只包含 gitea 指针和 src/maintenance/self/ 文档。
  • 外层 main 推送后，远端提交可以取得它引用的内层 Gitea 对象。
  • 外层已有的其他在制改动保持未暂存或原有暂存状态。

六、处理版本机制变化

如果上游更换迁移版本存储方式，或真实数据库来源无法由连续编号表达，本轮同步在最后一个已验证提交处结束，并记录来源分支、数据库版本、冲突编号和目标结构。获得明确的升级来源与目标后，再设计一次性转换。

这种处理让常规同步始终只维护 Gitea 原生版本状态，同时为真实出现的特殊升级保留明确输入和恢复点。

实现验收点

  • 错误记录包含来源、当前数据库版本、冲突迁移和预期目标结构。
  • 最后一个已验证提交可以检出、构建和运行。
  • 新转换方案开始前有可复现的数据库来源和升级目标。
