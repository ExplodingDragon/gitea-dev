上游同步流程

self 需要同时保留上游改进、两个功能 PR 的可追溯历史和自身数据库编号。同步流程围绕这三项事实展开，每次同步都形成可审阅的合并提交和迁移映射记录。

一、固定同步输入

同步前更新 upstream/main 和仍在维护的 PR 引用，并记录完整提交哈希。完整哈希让维护文档、合并父提交和测试结果指向同一份代码，即使 PR 后续继续提交也不会改变本次记录。

工作树应处于已提交状态，当前分支为 self。数据库映射表中的最后编号与 modelmigration/migrations.go 末尾需要一致。具备这些输入后，冲突才能明确归属于本轮上游变化，而不是混入尚未记录的本地修改。

实现验收点

  • 同步记录包含 upstream/main、相关 PR 和 self 起点的完整提交哈希。
  • 内外仓库在同步前只包含已经提交的维护历史。
  • 迁移映射表最后一项与代码中的最后迁移编号一致。

二、合并上游与 PR 更新

上游更新以双父合并提交进入 self，使共同祖先和上游提交保持可见。仍未进入上游的 PR 如果增加提交，也从上次固定的 PR 头继续合并。合并提交说明写明来源、固定提交和本次冲突范围。

Git 能直接合并的文件保留自动合并结果。发生冲突时先按领域分类：

  • 普通业务冲突组合双方当前行为，并通过调用顺序、事务范围和测试断言说明组合理由。
  • 数据库冲突以 self 现有迁移序列为准，为新迁移分配末尾下一个编号。
  • 生成文件由其项目规定的生成入口重新生成，并与来源输入一起提交。

如果两个业务实现对同一行为提出互斥语义，维护工作停在未提交的冲突状态，整理可观察行为后重新审阅。这个场景需要产品选择，简单叠加无法得到可靠结果。

实现验收点

  • 上游或 PR 更新通过具有两个父提交的合并提交进入 self。
  • 自动合并文件与来源分支一致，人工冲突文件有逐项理由和行为验证。
  • 互斥业务语义在形成合并提交前完成审阅。

三、映射数据库迁移

先读取 self 当前最后迁移编号，再按上游来源中的相对顺序逐项分配连续编号。每个文件改名为 pr-<来源>-v<self 编号>-patch<序号>.go，迁移函数本身保持来源实现；只有适配较新 Gitea 数据库 API 时才调整函数，并在逐项文档中说明原因。

映射完成后同时更新：

  1. modelmigration/migrations.go 的注册编号和顺序；
  2. migration-map.md 的来源编号与 self 编号；
  3. patches/ 中该迁移的结构和升级说明；
  4. database-versioning.md 的当前期望版本和来源范围。

数据库编号调整使用独立提交，提交差异只包含迁移列表、迁移文件和直接对应的迁移测试。这样上游业务变化与 self 版本变化可以分别复核。

实现验收点

  • 新迁移从现有末尾连续编号，ExpectedDBVersion() 等于最后迁移编号加一。
  • 文件名中的 PR、self 编号和 patchN 与映射文档一致。
  • 同一来源中的多项迁移保持原相对顺序。
  • 数据库记录提交不混入无关业务修改。

四、验证与固定外层仓库

Gitea 按仓库规范使用 Make 入口完成格式化、Go 静态检查、迁移测试、后端测试和适用的集成测试。迁移至少验证分叉点数据库可以依次执行所有 self 迁移，以及已知兼容来源只执行剩余迁移。具有 MySQL、PostgreSQL 或 SQL Server 测试环境时，使用 docs/testing.md 给出的对应 Make 入口验证实际方言。

验证完成后更新 verification.md，明确记录成功项、环境信息和上游基线同样存在的失败。随后在外层 self 分支固定 Gitea 子模块提交，并把代码指针与本轮维护文档一起提交。外层提交因此能够完整还原一轮可验证的 Gitea 状态。

实现验收点

  • 格式化、静态检查、迁移测试和后端测试使用 Gitea Make 目标执行。
  • 集成测试结果区分本轮回归与上游基线在同一环境中的结果。
  • 外层 self 提交固定已验证的 Gitea self 提交。
  • 验证记录包含执行日期、数据库类型、工具版本和未覆盖环境。

五、处理低收益异常

当来源迁移无法通过连续改号接入，例如上游更换版本存储机制或要求跨分支识别同号迁移内容时，本轮同步直接报告不受支持的来源和冲突编号，并保留可重新开始的干净提交点。维护者在获得明确升级需求后再设计一次性转换。

这种处理让常规同步始终使用 Gitea 原生机制，同时把极少发生、收益不明确的兼容工作留到真实需求出现时决定，避免长期维护一套没有实际来源使用的第二迁移系统。

实现验收点

  • 无法连续映射的来源会得到包含来源分支、数据库版本和冲突编号的明确错误记录。
  • 同步失败时最后一个已验证提交仍可检出和运行。
  • 新兼容方案在实现前具有明确的真实数据库来源和升级目标。
