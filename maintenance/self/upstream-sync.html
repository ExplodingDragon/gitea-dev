Gitea Pages 与 Codespace 设计文档

上游同步流程

一、固定同步输入

每轮开始时分别获取 upstream/main、Codespace PR #38337 和 Pages PR #40071 的当前头，并记录完整提交哈希。再确认内层位于 self、工作树干净、外层用户的其他改动保持原状。

固定提交让本轮结果可以重复审计，也为下一轮提供明确的增量起点。PR 头若已经包含目标上游提交，就由 PR 合并带入该上游历史。

实现验收点

  • 维护记录包含三个来源的完整提交哈希和获取日期。
  • 开始合并前，内层分支为 self 且没有未提交文件。
  • 上次同步的两个 PR 头均可从当前 self 历史解析。

二、按正常方式合并业务代码

先合并包含主要业务变化的 PR，再合并另一个 PR 的最新头。两个合并都保留第二父，使 PR 原始提交和作者顺序完整进入 self。非数据库冲突按两个功能正常组合后的行为解决，例如仓库转移同时满足上游通知、Codespace 写锁和 Pages 生命周期更新。

合并完成后检查来源祖先关系，并比较每个合并相对第一父的文件差异。这个步骤确认业务代码来自固定 PR 头，而不是维护分支重新实现的一套近似逻辑。

实现验收点

  • 每个 PR 更新都有对应的双父合并提交。
  • 两个固定 PR 头和目标上游提交均为新 self 的祖先。
  • 非数据库冲突的结果覆盖双方已有测试所表达的行为。

三、安排数据库迁移

对比上次与本次来源头的 modelmigration 变化，逐项判断它属于全新来源迁移，还是对已经进入 self 的来源迁移追加内容。文件名使用 pr-<来源 PR>-v<来源迁移编号>-patch<N> 保存稳定来源身份，实际执行位置统一追加到 self 迁移列表末尾。

来源的完整建表迁移若已经由 self 早期迁移执行，就比较结构差异并只移植增量。上游新增迁移若与 self 已发布编号冲突，则保持实现内容，重新安排到 self 的连续末尾编号。这样旧 self 实例能沿原生迁移器升级，非数据库代码仍与来源一致。

实现验收点

  • 每项来源数据库变化都在迁移映射中有唯一记录。
  • self 迁移编号从上一项开始连续递增。
  • 已发布迁移的来源增量拥有独立实现和直接测试。

四、验证代码与升级路径

使用 Gitea 仓库规定的 Make 目标执行格式化、依赖整理、生成检查、静态检查、构建、迁移测试、完整后端测试、前端测试、集成测试和端到端测试。迁移直接测试至少覆盖重复执行、保留数据和本次关键结构变化。

集成测试的环境差异需要记录测试名、工具版本、实际值和期望值；与本轮无关且经用户确认的既知差异可以保留记录，其他失败继续修复。完成后执行 make clean，确保测试二进制和临时目录不进入提交。

实现验收点

  • Gitea 测试均从仓库 Make 目标启动。
  • 数据库版本从上一版 self 实际升级到新期望版本。
  • 清理后内层工作树干净，没有测试二进制或临时集成目录。

五、更新维护文档

同步更新总览、数据库版本、迁移映射、Git 历史、冲突记录、逐项迁移说明和验证记录。文档说明每项设计为什么这样安排，并把结果转成可验证行为。

文件名中的来源迁移编号与 self 实际编号分别记录，防止下一轮因为上游顺延迁移而误改维护文件身份。文档构建通过后，再固定外层子模块指针。

实现验收点

  • 每个设计章节末尾都有“实现验收点”。
  • 所有提交、来源头、迁移编号和期望版本与代码一致。
  • src/SUMMARY.md 能进入全部当前逐项迁移说明。

六、提交与推送

先提交并推送内层 gitea/self，确认远端 self 指向本轮最终提交。然后在外层只暂存 gitea 子模块指针、src/maintenance/self/ 和 src/SUMMARY.md，提交并推送 gitea-dev/main。

这个顺序保证外层记录引用的内层提交已经在远端可获取，同时保护外层其他子模块和设计文档中的用户改动。每次推送前重新获取远端分支，确认没有未接入的新提交。

实现验收点

  • origin/self 与内层本地 self 指向同一提交。
  • 外层维护提交只包含 Gitea 指针和本轮维护文档。
  • origin/main 与外层本地 main 指向同一提交，其他用户改动仍保持未暂存状态。
