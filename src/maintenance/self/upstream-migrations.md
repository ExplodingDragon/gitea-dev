# 官方迁移接入记录

## 保留官方文件身份

上游正式发布的迁移继续使用 `modelmigration/v29/vXXX.go` 路径，文件内容和配套测试保持原样。self 已经发布了不同的 365—367，因此只在 `migrations.go` 中调整这些函数的执行位置，不通过文件重命名表达 self 编号。

这样设计的原因是官方文件名属于上游演进历史。保持它们不变，可以直接检查内容一致性，也让上游未来的 `v370.go`、`v371.go` 正常进入仓库，不会与本项目自定义命名占用同一位置。

**实现验收点**

- 官方 `v365.go` 至 `v369.go` 保持原路径。
- 官方已有的 `v365_test.go`、`v366_test.go`、`v368_test.go`、`v369_test.go` 保持原路径和内容。
- 九个文件与 `upstream/main@23836eb610b6673dc4ef7001d432e48dd3af1537` 逐字一致。

上一版维护方案曾把官方 `v365`—`v367` 改名为三个 `pr-*` 文件。提交 `f19882d9babed0ecd7526607c5cc364cd51d7a81` 以百分之百重命名恢复官方路径，没有改动函数或测试内容。官方 PR #39998、#40231、#40214 的三篇旧补丁文档随之合并到本页，因为这些变化现在按官方迁移管理。

该整理特意保留在独立提交中，后续审阅可以区分“文件身份恢复”和“新增迁移执行编号”，也能防止维护时再次把官方文件改成自维护 PR 格式。

**实现验收点**

## 后续官方迁移接入

上游新增官方迁移时，直接保留它的 `vXXX.go` 与测试。若官方编号在 self 中尚未使用，也仍以 self 当前末尾编号注册，因为已发布 self 数据库只能向末尾追加；文件名继续表示官方身份，映射表表示 self 执行位置。

这种统一做法让每轮更新只需要回答两个明确问题：官方文件是否与上游一致，以及旧 self 数据库将从哪个编号执行它。

**实现验收点**

- 新官方文件可以使用 `git diff upstream/main -- modelmigration/v29/vXXX.go` 直接审计。
- 新函数注册在 self 当前连续末尾，不改变已发布编号。
- 新增记录同步更新本页、迁移映射、数据库版本和升级测试。
