## 两个 PR 当前完整迁移的关系

Codespace 与 Pages 当前头都包含上游数据库版本 370，因此各自在 `modelmigration/v29/v370.go` 放置完整功能迁移。self 已经在 365—367 执行 Codespace、Pages 和 Manager 注册令牌结构，又在 371 执行 Codespace 的后续索引清理，所以不会再次注册两个 PR 的完整 `v370.go`。

这不是舍弃 PR 的数据库变化，而是把当前完整结构拆解为 self 已经发布的四项增量。业务代码仍直接来自 PR 当前头；数据库只保留现有 self 实例真正需要执行的变化。

**实现验收点**

- `AddCodespaceTables`、`AddPagesTables`、`AddCodespaceManagerRegistrationTokenTable` 各注册一次。
- `DropCodespaceQueuedTimeoutIndex` 注册为 371，并有直接测试。
- self 通过四项增量得到两个 PR 的当前数据库结构，官方后续 `v370.go` 位置保持可用。

## 官方文件与 self 编号的关系

官方文件名不等于 self 实际编号。`v365.go`、`v366.go`、`v367.go` 在 self 中分别执行为 368、369、370；`v368.go`、`v369.go` 分别执行为 372、373。中间的 self 371 是 Codespace 已发布迁移的第三项增量。

保留官方文件原名可以让未来上游继续增加 `v370.go`，而不会与维护分支曾经改名的文件冲突。实际顺序集中在 `migrations.go` 和本表中，避免用文件名猜测 self 执行位置。

**实现验收点**

- 五个官方实现文件及其现有测试与 `upstream/main@23836eb610` 一致。
- [官方迁移接入记录](upstream-migrations.md)列出五项完整对应关系。
- `migrations.go` 是 self 实际执行编号的唯一代码依据。

## 后续更新方法

下一轮先比较固定来源头之间的数据库差异，再判断变化属于自维护 PR 增量还是官方新迁移。自维护增量沿已有来源身份增加 `patchN`；官方迁移保持 `vXXX` 文件身份。两类变化都追加到 self 当前末尾编号，并同步加入真实升级测试或直接迁移测试。

这个方法避免把上游正式文件误当作本项目补丁，也避免已经发布的 self 编号因上游更新被重新解释。

**实现验收点**

- 新映射包含来源提交、文件身份、self 编号和完成后版本。
- 自维护 PR 的 `patchN` 与同一来源的历史顺序一致。
- 官方文件比较、self 升级测试和映射文档在同一轮更新中完成。
