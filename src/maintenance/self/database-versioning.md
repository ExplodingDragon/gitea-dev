# 数据库版本与升级范围

## 编号含义

Gitea 的迁移编号和数据库版本相差一。`newMigration(365, ...)` 执行成功后，`version` 表记录的数据库版本是 366；迁移 366 执行成功后，数据库版本是 367。Gitea 使用这个关系计算待执行迁移，并检查迁移编号是否连续。

当前上游基线的最后一项迁移是 364，所以分叉点的期望数据库版本是 365。`self` 在其后追加 Codespace 365 和 Pages 366，最终期望数据库版本为 367。

| 执行阶段 | 最后一项迁移编号 | 数据库版本 | 数据库含义 |
| --- | ---: | ---: | --- |
| 上游分叉点 | 364 | 365 | 尚未建立 Codespace 和 Pages 表 |
| `self` Codespace 完成 | 365 | 366 | 已建立 Codespace 表 |
| `self` Pages 完成 | 366 | 367 | 已建立 Codespace 和 Pages 表 |

保留 Gitea 原生版本关系的原因是启动检查、命令行迁移和测试都能继续依据同一序列工作；维护者只需查看迁移列表末尾即可确定下一编号。

## 当前迁移顺序

`modelmigration/migrations.go` 的末尾顺序为：

```go
newMigration(364, "Add new table project_workflow", v29.AddProjectWorkflow),
newMigration(365, "Add Codespace tables", v29.AddCodespaceTables),
newMigration(366, "Add Pages support", v29.AddPagesTables),
```

Codespace 先于 Pages 是因为当前可接受的单 PR 数据库来源是 Codespace PR #38337。明确来自该 PR、数据库版本为 366 的实例已经执行了与 `self` 相同含义的迁移 365，进入 `self` 后只需执行 Pages 366。

## 可接受的升级来源

| 数据库来源 | 进入 `self` 时的版本 | 处理方式 | 结果 |
| --- | ---: | --- | --- |
| 全新安装 | 未初始化 | 由 Gitea 建表和原生迁移流程建立完整结构 | 367 |
| 分叉前的上游版本 | 不高于 365 | 按原生顺序执行尚未完成的迁移，包括 365、366 | 367 |
| 明确由 Codespace PR #38337 建立 | 366 | 迁移 365 已具有 Codespace 含义，只执行 Pages 366 | 367 |
| 已经运行 `self` | 367 及后续 `self` 版本 | 执行以后追加的连续 `self` 迁移 | 最新 `self` 版本 |

版本 366 本身不能说明迁移 365 的业务含义，因此升级记录还需要保存来源分支。Pages PR #40071 单独建立的版本 366 表示“迁移 365 已建立 Pages 表”，与 `self` 的“迁移 365 已建立 Codespace 表”不同。分叉后上游如果也使用迁移 365，同样会产生新的含义。这两类数据库转入 `self` 时使用进入相应分支前的备份重新升级，保证版本号和实际表结构一致。

这种直接分支关系是本项目明确选择的维护方式：进入 `self` 后继续使用 `self` 二进制和迁移序列。项目无需为多个同号迁移建立额外识别表，因为部署记录已经确定数据库来源，原生版本表可以保持简单且可靠。

## 文件命名与后续编号

`self` 来源迁移文件采用：

```text
pr-<来源 PR>-v<self 迁移编号>-patch<该 PR 的迁移序号>.go
```

各字段含义如下：

- `来源 PR` 说明业务实现来自哪个上游 PR。
- `v` 后的数字是文件在 `self` 中实际注册的迁移编号，也是维护时判断执行顺序的依据。
- `patch` 后的数字是该来源 PR 在 `self` 中产生数据库迁移的顺序，从 1 连续增加。

例如，Codespace 的下一项数据库修正如果占用 `self` 迁移 367，文件名为 `pr-38337-v367-patch2.go`。Pages 的下一项修正如果随后占用迁移 368，文件名为 `pr-40071-v368-patch2.go`。

未来上游 PR 自带迁移时，也按 `self` 的下一个可用编号追加。例如，上游 PR #40123 的原始迁移 365 在 `self` 中下一个可用编号为 367，则文件命名为 `pr-40123-v367-patch1.go`，迁移映射同时记录原始编号 365 和 `self` 编号 367。这样文件名始终反映实际执行位置，上游编号仍可从文档追溯。

## 迁移实施方式

新迁移直接在对应 `modelmigration/vNN` 包中实现，并追加到 `modelmigration/migrations.go` 末尾。编号采用当前最后编号加一；实现复用 Gitea 的数据库抽象和既有多数据库写法。执行失败由原生迁移命令返回具体错误，修复后继续通过同一入口验证。

当上游对迁移框架本身进行结构调整、导致现有追加方式无法保持连续编号时，维护工作以明确错误停止并重新审阅设计。这个低频场景不预先增加兼容层，因为额外执行器会让安装、启动检查和维护记录产生两套状态，收益小于长期维护成本。

## 实现验收点

- 迁移列表末尾依次为 364、365、366，没有重复或跳号。
- `ExpectedDBVersion()` 对当前 `self` 返回 367。
- 数据库版本 365 会执行 Codespace 365 和 Pages 366；明确来自 Codespace PR 的版本 366 只执行 Pages 366。
- 迁移文件名中的 `vNNN` 与 `migrations.go` 中实际注册编号一致。
- 同一 PR 的 `patchN` 按该 PR 在 `self` 中新增迁移的顺序连续编号。
- 每项移植迁移同时记录来源编号和 `self` 编号，后续维护者可以还原编号变化原因。
