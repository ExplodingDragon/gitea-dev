# 数据库版本与升级范围

## 编号含义与当前序列

Gitea 的迁移编号和数据库版本相差一。迁移 365 执行成功后，`version` 表记录 366；迁移 367 执行成功后，数据库版本为 368。`self` 直接使用这套原生关系，安装、启动检查、`gitea migrate` 和迁移测试都从同一列表计算待执行项。

当前迁移列表末尾为：

```go
newMigration(364, "Add new table project_workflow", v29.AddProjectWorkflow),
newMigration(365, "Add Codespace tables", v29.AddCodespaceTables),
newMigration(366, "Add Pages support", v29.AddPagesTables),
newMigration(367, "Add Codespace Manager registration token table", v29.AddCodespaceManagerRegistrationTokenTable),
```

| 执行阶段 | 最后一项迁移编号 | 数据库版本 | 数据库结构含义 |
| --- | ---: | ---: | --- |
| 上游分叉点 | 364 | 365 | 尚未建立 Codespace 和 Pages 表 |
| Codespace 基础迁移完成 | 365 | 366 | 已建立 Codespace 基础表 |
| Pages 基础迁移完成 | 366 | 367 | 已建立 Codespace 和 Pages 表 |
| Manager 注册令牌迁移完成 | 367 | 368 | 已建立按作用域注册 Manager 所需的令牌表 |

**实现验收点**

- 迁移列表末尾依次为 364、365、366、367，没有重复或跳号。
- `ExpectedDBVersion()` 对当前 `self` 返回 368。
- 每个表格阶段的数据库版本都等于最后迁移编号加一。

## 为什么把注册令牌表放在迁移 367

PR #38337 的提交 `3fc98fc1c089092a2d77978f8d070fe595f595f2` 把注册令牌表追加到来源迁移 365。`self` 的迁移 365 已经作为可运行版本发布，并且迁移 366 已由 Pages 使用。已经运行旧 `self` 的数据库版本为 367，它不会重新执行迁移 365，因此新表必须出现在下一个迁移 367 才能覆盖这类数据库。

迁移 367 只建立 `codespace_manager_registration_token` 表。新安装和低版本升级会依次执行 365、366、367；旧 `self` 数据库只执行 367。两条路径最后得到相同结构，业务代码仍保持 PR #38337 的当前实现。

**实现验收点**

- `pr-38337-v365-patch1.go` 不包含 `codespace_manager_registration_token` 表。
- `pr-38337-v367-patch2.go` 独立定义并同步该表。
- 数据库版本 367 启动当前 `self` 时会执行迁移 367 并推进到 368。
- 数据库版本 365 会按 365、366、367 的顺序完成全部三项功能迁移。

## 可接受的升级来源

`self` 的数据库版本含义由分支历史确定。项目直接支持分叉前的低版本、明确来自 Codespace PR 的数据库和既有 `self` 数据库；这些来源都能由原生迁移序列闭环升级。

| 数据库来源 | 进入当前 `self` 时的版本 | 原生迁移行为 | 最终版本 |
| --- | ---: | --- | ---: |
| 全新安装 | 未初始化 | 建表后执行完整当前序列 | 368 |
| 分叉前的上游版本 | 不高于 365 | 依次执行尚未完成的 365、366、367 | 368 |
| Codespace PR #38337 旧版本 | 366 | 执行 Pages 366 和注册令牌 367 | 368 |
| Codespace PR #38337 当前版本 | 366，迁移 365 已含令牌表 | Pages 366 后由迁移 367 幂等确认令牌表结构 | 368 |
| 上一版 `self` | 367 | 只执行注册令牌 367 | 368 |
| 当前及后续 `self` | 368 及后续 `self` 版本 | 执行以后追加的连续 `self` 迁移 | 最新 `self` 版本 |

Pages PR 单独建立的数据库把版本 366 解释为“Pages 已完成”，而 `self` 把同一版本解释为“Codespace 基础迁移已完成”。分叉后的上游也可能为相同版本号赋予其他结构含义。这些数据库直接采用各自分支后续版本；需要转入 `self` 时，从进入相应分支前的备份按 `self` 顺序升级。项目选择清晰的分支升级关系，是因为单一原生版本表比额外识别同号迁移内容更容易审计和恢复。

**实现验收点**

- 部署记录可以指出数据库来自分叉前上游、Codespace PR 或 `self`。
- 表中五类可接受来源都能只通过 Gitea 原生迁移入口到达当前版本 368。
- Pages 单独数据库和分叉后上游数据库有明确的备份转入路径，不需要额外迁移识别表。

## 文件命名与后续编号

`self` 的来源迁移文件采用：

```text
pr-<来源 PR>-v<self 迁移编号>-patch<该 PR 的迁移序号>.go
```

- `来源 PR` 说明数据库变化来自哪个上游功能历史。
- `v` 后的数字是 `self` 中实际注册的迁移编号。
- `patch` 后的数字是该 PR 在 `self` 中产生数据库迁移的顺序。

当前 Codespace 使用 `patch1` 对应迁移 365，`patch2` 对应迁移 367；Pages 使用 `patch1` 对应迁移 366。下一项 Codespace 数据库变化使用 `pr-38337-v368-patch3.go`，如果随后出现 Pages 数据库变化，则使用 `pr-40071-v369-patch2.go`。文件名直接表达实际执行位置，来源中的原始编号保存在迁移映射文档。

**实现验收点**

- 文件名中的 `vNNN` 与 `migrations.go` 注册编号一致。
- 同一 PR 的 `patchN` 按进入 `self` 的数据库变化顺序连续增加。
- 下一个可用迁移编号为 368，下一个 Codespace patch 序号为 3，Pages patch 序号为 2。

## 迁移实施方式

新迁移在对应 `modelmigration/vNN` 包中实现，并追加到迁移列表末尾。来源 PR 修改尚未进入 `self` 的新迁移时，按来源相对顺序移植；来源 PR 修改已经进入 `self` 的旧迁移时，现有文件保持已发布结构，新增部分写入下一项 patch。直接测试覆盖建表幂等性、必要索引和业务依赖的数据库约束。

如果未来上游更换版本存储机制，使连续追加不能表达真实升级顺序，维护流程以明确错误结束本轮同步，并基于实际数据库来源重新设计一次性转换。常规同步继续只维护一套 Gitea 原生迁移状态。

**实现验收点**

- 新迁移编号等于当前最后编号加一。
- 迁移记录提交只包含迁移列表、实现和直接测试。
- 迁移直接测试至少验证重复执行和业务依赖的关键约束。
- 版本机制变化时，错误记录包含数据库来源、当前版本和无法连续安排的迁移编号。
