## 升级承诺与本次一次性清理

self 保证沿自身历史运行的数据库继续升级。当前直接验证上一版 374 → 375，并保留 372 → 375 的跨版本测试。全新安装直接创建当前结构。官方分支及两个独立 PR 在迁移 365 后具有不同编号含义；这些已安装数据库需要按明确来源另行设计转换。

本次 Codespace 改为数字实例 ID 和创建时的密钥快照。按已审阅方案，迁移 374 删除全部旧 Codespace 实例、实例令牌、实例 SSH 公钥和旧日志，用户随后重新创建实例。个人密钥密文、Manager 及注册令牌、模板、仓库权限授权保持原值；个人密钥旧仓库关联和旧字段按新 PR 结构移除。其他 Gitea、Pages 数据沿正常业务维护。

“可升级”表示迁移可以完成、保留项维持原值，并不表示保留旧 Codespace 工作目录。部署时还要按 [patch4 部署说明](patches/pr-38337-v365-patch4.md) 清理对应站点的旧运行资源并更新配套组件。数据库迁移不会连接 Kubernetes。

**实现验收点**

- 完整迁移器执行 374 → 375 和 372 → 375，版本只在迁移成功后推进。
- 清理范围、保留范围及个人密钥新语义有直接测试。
- 375 再次启动时，新建实例和凭据保持不变。
- 发布前完成旧运行资源清理、配套版本核对和新实例创建验证。

## 文件身份与后续维护

官方 `vXXX.go` 和对应测试保持原路径、原内容；self 执行位置由 `migrations.go` 决定。Codespace、Pages 使用稳定的 `pr-<PR>-v<最初来源>-patch<N>` 身份。本轮新增 `pr-38337-v365-patch4.go`，注册为 self 374，完成后为 375。

这样区分来源身份和执行编号，可以保留官方文件的后续合并位置，同时让已发布 self 历史继续向末尾追加。已发布 patch1—patch3 保持原样，patch4 仅处理本次结构变化。

**实现验收点**

- [迁移映射](migration-map.md) 与代码中的 365—374 连续列表一致。
- 官方迁移可与固定主线逐字比较，历史 PR 迁移可与上一版 self 逐字比较。
- 后续变化从 self 375 追加，按实际变化确定新的官方迁移或 PR patch。
