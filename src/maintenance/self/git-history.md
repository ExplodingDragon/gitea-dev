**实现验收点**

- 图中六个提交都可以由 `git rev-parse` 解析。
- `31061a3800` 和 `53d76a7ab0` 各有两个父提交。
- `e401021a12` 和 `dc1a1f5b68` 各有一个父提交。

## 祖先关系与同步位置

当前固定的三个来源为：

- `upstream/main@c74f2f921678fcb39b02852f566070fcae82a127`；
- Codespace PR #38337 `68bcefaa69a3075e0b805abcaa34d2504d493fb7`；
- Pages PR #40071 `e645501a8168070aa6daeee2789d8c4616c8b985`。

Codespace 和 Pages 两个头都以当前上游提交为父，因此任何一项 PR 的正常业务更新都能连同共同上游进入 `self`。分别保留两个双父合并，是为了让下一轮 Git 能以各自 PR 头计算增量，而不是重新比较完整功能分支。

**实现验收点**

- 对三个固定来源执行 `git merge-base --is-ancestor <来源> self` 均返回成功。
- 两个 PR 头的历史都包含 `c74f2f9216`。
- 下一轮可以分别以 `68bcefaa69` 和 `e645501a81` 作为各 PR 的上次同步点。

## 后续历史组织

下一轮先获取上游与两个 PR 的新头，再按正常双父合并接入非数据库代码。若 PR 已包含目标上游提交，无需另外制造上游合并；两个 PR 仍分别留下合并记录，以保存来源边界。

数据库变化在功能合并之后使用普通提交安排。提交说明同时写明来源迁移身份和 `self` 实际编号；直接测试与实现放在同一迁移提交中。这样 Git 历史能够回答“代码来自哪里”和“旧实例何时执行数据库变化”两个不同问题。

**实现验收点**

- 新来源头通过第二父可追溯，原始提交哈希保持不变。
- 新迁移提交只处理迁移列表、迁移实现、直接测试和必要文件名整理。
- 每轮完成后，外层仓库固定新的内层提交并同步更新维护文档。
