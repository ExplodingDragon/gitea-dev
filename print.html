本目录汇总 Gitea 相关功能的产品设计、系统边界、接口约定和实现验收点。文档按功能分组，Pages 和 Codespace 分别描述各自的管理职责、运行组件、数据模型与生命周期；它们可以独立实现和部署。

文档分组

  • Gitea Codespace：远程开发环境的业务管理、运行平台、协议、部署要求和测试方式。

Gitea Pages 总体设计

Gitea Pages 由 Gitea 管理面和独立 Pages 实例组成。Gitea 保存站点当前事实、接收或生成网站成品，并把事实提供给所有登记实例；每个 Pages 实例在自己的机器上主动同步、展开并提供静态网站。访客请求只访问已经部署的本地内容，因此 Gitea 暂时不可用不会影响已经生效的网站。

Pages 网站使用公开访问方式。源码仓库可以是私有仓库，但启用 Pages 后网站仍然公开；公开仓库转为私有仓库时，Gitea 会关闭已经启用的站点，仓库管理员可以再次确认并启用公开网站。

核心行为

每个仓库最多一个 Pages 站点，创建后默认关闭。仓库名为 .pages 时提供所有者主页，其他仓库提供项目站点：

https://<owner>.<pages-instance>/<repo>/
https://<owner>.<pages-instance>/       # <owner>/.pages

外部地址使用当前所有者和仓库名称，内部目录、结果和清理使用 repo_id。改名、所有者改名和转移会更新外部路由，但不会复制网站内容或改变站点身份。

仓库设置提供两种自动发布方式：artifact 接受同仓库 Actions 成品，branch 定期把指定分支目录打包。网页/API 上传是随时可用的显式版本操作，不会改变自动发布方式。分支、Actions 和上传产生的内容最终都形成一个网站根目录 TAR.GZ。Gitea 按摘要保存可恢复的内容版本并为站点选择一个当前版本；相同内容复用已有版本。Pages 实例只同步当前摘要，因此内容历史不会增加实例协议和本机部署状态。Gitea 先确认版本已保存，再由每个 Pages 实例主动下载、检查、展开和发布；版本已准备、内容已安装和地址已可访问是三个独立状态。

全局管理员登记 Pages 实例。所有实例都处理所有启用站点，实例之间不组成集群，也不由 Gitea 选择某台机器承载某个站点。实例使用单机内嵌 etcd 保存本机状态，网站文件、证书和服务配置保存在本机数据目录。Gitea 使用现有存储抽象保存 TAR.GZ，Pages 通过带实例凭据的 Gitea 内部接口下载，不需要访问 Gitea 存储后端。

自定义域名先由 Gitea 定期检查业务 TXT 所有权，Pages 也在本机持续检查。全局管理员通过 Gitea [pages] 配置统一设置两端是否要求这项条件；两端各自配置递归 DNS 和刷新周期，默认每 15 分钟检查一次。域名成功验证后，后续解析失败在最近成功后的 24 小时内保留当前入口，避免一次 DNS 故障立即中断网站；从未成功的域名不能启用。这不改变证书颁发机构的域名控制验证。Pages 自管 HTTPS 时，用户自定义域名使用 HTTP-01，默认域名使用 DNS-01，证书和私钥由该实例保存；前置代理模式的 TLS 由代理负责。

Gitea 的两个 Pages 计划任务分别负责分支来源检查和业务 TXT 检查，最短周期为 1 分钟。Pages 的部署、归档展开、TXT 和证书维护在实例本地异步完成；访客请求只读取已经部署的本地内容。标准程序提供 HTTP、前置代理源站和 Pages 自管 HTTPS 三种责任模式。Pages 根包也可以作为 Go 依赖使用：同步和安全检查保持不变，使用者通过统一发布器把已检查内容接入自己的 Web 服务。网站成品只要求包含普通文件，不以 index.html 作为发布条件。

  • 新仓库的 Pages 站点默认关闭，.pages 和普通仓库的地址、改名转移规则符合本章定义。
  • 两种自动发布方式与显式上传都能产生同一种 TAR.GZ，并分别显示成品准备、内容安装和地址发布结果。
  • Gitea 保留可配置数量的内容版本，历史版本可以恢复；实例只接收恢复后选定的当前摘要。
  • 每个登记实例都主动部署全部启用站点；访客请求只访问本机已部署内容。
  • Gitea 存储后端、Pages 本地状态、证书材料和路由配置按职责分离，Pages 不读取 Gitea 后端凭据。

  • 内置 HTTP 服务和外部 Go 发布器使用同一主动部署流程；没有 index.html 的成品仍能发布并访问实际文件。

工程入口与验证

本章说明 Gitea 与 Pages 的代码边界、程序入口和验证方式。业务行为由其余章节定义，工程结构把这些行为落实到可以独立构建和测试的模块。

仓库、模块与程序入口

Gitea 与 Pages 是两个独立工程。Gitea 负责仓库管理、版本历史、数据库、成品存储和内部接口；Pages 负责同步当前目标、TAR.GZ 展开、本机状态、网站服务和证书。两边只通过通信协议交换当前事实、当前成品和部署结果。

位置作用
顶层工作区使用 main，设计文档位于 src/pages/。
gitea/Gitea 独立 Git 仓库，Pages 功能分支为 feat-pages。
gitea-page/独立 Go 模块，模块路径为 gitea.dev/page，根包为 page。
gitea-page/page.go稳定公共门面，提供配置、服务生命周期、内容和发布接口。
gitea-page/internal/runtime/同步、etcd、归档、内置 HTTP、TXT、证书与 ACME 实现。
gitea-page/cmd/main.gogitea-pages 进程入口，读取 YAML、建立信号上下文并运行公共入口。

标准程序使用一个启动形式：

gitea-pages --config /etc/gitea-pages/config.yaml

命令使用标准库参数解析。page.LoadConfig 严格读取一个 YAML 文档，page.Run 组装内置 HTTP 发布器、同步服务和优雅关闭。内置 HTTP 通过配置选择纯 HTTP、前置代理源站或 Pages 自管 HTTPS；这个选择只改变 Web 与证书责任，不改变同步和部署状态机。

Pages 使用 github.com/go-acme/lego/v5 实现 ACME，并通过 lego provider 注册表选择默认域名的 DNS 服务商；YAML 直接使用所选 provider 的参数名，使服务商认证和 DNS 行为继续由 lego 维护。Pages 使用 go.etcd.io/etcd/server/v3/embed 保存单机运行状态。Gitea 侧遵循仓库 AGENTS.md 与测试文档；Pages 侧使用模块 Make 目标完成格式化、静态检查、测试和构建。

实现验收点

  • Gitea 与 Pages 可以分别解析依赖并构建，版本历史与当前部署通过内部接口连接。
  • go build ./cmd 生成只有 --config 启动参数的 gitea-pages。
  • YAML 未知字段、额外文档和模式组合错误在启动阶段得到具体错误。
  • DNS-01 provider 在 listener 与同步任务启动前完成构造，未知 provider 或无效参数会让标准程序直接返回错误。
  • page.Run 在 listener 可以接收连接后启动同步，退出信号会关闭同步、HTTP 服务和内嵌 etcd。
  • 模块公共门面位于根包，Gitea 协议、同步器、存储和证书细节保持在 internal/runtime。

Pages 内部边界

Service 负责实例注册、全量与增量同步、当前 TAR.GZ 下载、摘要检查、归档安全、业务 TXT 和结果上报。Publisher 只接收已经展开的不可变 Content，负责把 Deployment 映射为实际网站入口。标准 page.Run 使用包内 HTTP 发布器；外部 Go 程序实现同一接口后使用 page.NewService。

同步实现按职责分文件：store.go 与 store_content.go 保存当前事实和不可变内容；sync_protocol.go 处理全量、补查和增量同步；sync_deploy.go 处理候选部署事务；sync_certificates.go 处理证书维护；dns_provider.go 负责从 YAML 参数构造 lego provider；address.go 计算所有者 Host 与项目路径；server.go 提供内置 HTTP 路由；config.go 解析 YAML；application.go 组装标准进程。

有界部署队列只保存仓库 ID。工作线程开始时从 etcd 读取最新事实，因此排队期间到达的新摘要、名称或域名会自然生效。同一仓库正在部署时再次更新，当前任务结束后再处理一次最新目标。进程取得数据根目录锁后重建工作目录；已确认内容保存在独立站点目录。

下载和展开先产生候选内容。Publisher.Publish 成功后才保存当前安装摘要并清理旧内容；发布器返回错误时先恢复旧入口，核心删除失败候选。关闭和删除先移除入口，再清理内容。部署结果保存前重新核对站点时间、当前摘要和路由事实，迟到任务不能覆盖更新后的站点。结果无法写入 etcd 时继续通过 Gitea 结果接口报告当前故障。

实现验收点

  • Service 与 Publisher 的职责可以独立测试，外部发布器无需重复同步和归档安全逻辑。
  • Publisher.Restore 以迭代器提供本机确认部署，大量站点不需要复制为完整切片。
  • 队列项执行时读取最新事实，同一仓库调用串行，不同仓库按配置并行。
  • 工作目录在持锁后重建，已确认站点目录保持不变。
  • 发布错误保留旧入口；成功发布替代内容后只保留当前摘要目录。
  • 结果写入核对当前状态，etcd 写入故障仍会尝试向 Gitea 报告。
  • DNS provider 构造与证书维护保持在证书边界内，provider 参数只在构造期间进入进程环境，构造完成后恢复原值。

Gitea 代码边界

Gitea 侧沿用现有分层：models/pages 负责五张表和稳定查询，modules/pages 负责 TAR.GZ 检查与存储路径，services/pages 负责设置、版本提交、恢复、删除、生命周期和结果事务，路由层只完成请求解析、权限检查和响应转换。

services/pages/address.go 集中处理所有者 DNS 标签、实例根地址、自定义 Host 规范化和域名命名空间冲突。域名使用 golang.org/x/net/idna 查询映射、双向文字和 DNS 长度检查；Pages 服务只补充多标签、IP 地址和平台命名空间规则。仓库设置页、版本页、Actions 摘要、实例登记和域名登记因此使用同一套地址函数。

settings.go 处理站点开关和自动发布来源，publish.go 处理成品检查、版本提交、恢复、删除和保留。两者复用同一个仓库站点锁和站点更新时间。仓库关闭、改名、转移、所有者改名和删除通过对应服务事务推进站点时间，使仓库变化与 Pages 通知使用同一提交顺序。

modules/setting 保存归档大小、条目数、版本保留数、批量大小、TXT 周期和 DNS 地址等启动配置。services/pages 把资源字段组装为 modules/pages.Limits。内容使用 Gitea storage 抽象，临时上传使用 Gitea Dropzone 和临时上传模型，仓库提交使用现有锁抽象；实例凭据复用安全随机数、HTTP Authorization、SHA-256 和恒定时间比较工具。

Pages 内容 API 和网页共用版本服务。版本列表按 ID 倒序使用 Gitea 标准分页，并批量读取当前页的 Actions 来源。设置页只读取来源、来源错误和域名配置；版本页展示摘要、首次来源、创建时间与 Current 状态，Current 可查看实例详情或删除，历史版本可恢复或删除。全局管理页使用标准管理表格显示实例 ID、公开根地址、最近通信时间和紧凑操作。

实例创建和重置使用 POST 后重定向到 GET。一次性明文令牌暂存在当前管理员会话，首次 GET 显示并消费，刷新不会重复操作。管理页面复制原始令牌，运维把它写入 Pages YAML 的 gitea.token。

Actions 成品提交在 Pages 版本事务中把所属 ActionRun.HasPagesArtifact 单调设置为真。运行详情只有该标记存在时才查询当前默认 Pages 地址并显示提交事实；实例结果继续表示当前站点，而不解释为历史运行结果。

实现验收点

  • 模型、通用模块、业务服务和路由保持 Gitea 现有依赖方向。
  • 地址规范化、所有者编码、项目路径和命名空间冲突由同一服务模块处理。
  • 来源设置与版本操作各有一个事务入口，并复用站点锁与更新时间。
  • 仓库生命周期变化和 Pages 状态在同一事务顺序中提交，失败时共同回滚。
  • Pages 成品存储、临时上传、锁、凭据和时间工具复用 Gitea 现有实现。
  • 设置页与版本页各自只加载所需数据；版本分页批量读取 Actions 来源，没有逐行查询。
  • Current、历史版本和最后一个版本都能按页面确认流程删除；Current 详情按实例显示当前结果。
  • 实例创建和重置重定向到 GET，一次性令牌只显示一次并可以复制到 YAML。
  • Actions 标记、版本创建和当前指针在同一事务中生效，普通运行不增加 Pages 查询。

启动、文档与验证

标准程序从 YAML 得到 Gitea 地址、令牌、公开根地址、数据根目录、监听器、同步、DNS 与证书配置。DNS-01 使用一个 provider 名称和一组 lego 参数，标准构建包含完整 provider 注册表；关注依赖体积的自定义构建使用 lego 官方轻量标签选择所需 provider。三种 HTTPS 责任模式的配置和目录见数据与本地架构，证书行为见证书管理。作为 Go 依赖时，调用方可以直接构造 page.Config，注入日志与 HTTP 客户端，并用自定义 Publisher 运行 Service。

Pages 模块使用以下入口：

make format
make check

make check 包含格式检查、go vet ./...、go test ./... 和 go build ./...。Gitea 使用仓库 Make 目标；后端与模板修改分别运行对应 lint，集成测试按 make test-integration#TestName 执行。根设计文档使用 mdBook 构建，并检查 Markdown 链接和 Mermaid 语法。

验证围绕行为而不是内部字段数量：配置能否明确责任、当前成品能否安全部署、旧内容能否在失败时保留、Gitea 能否看到当前结果，以及清空本地状态后能否全部恢复。这样实现可以在保持外部行为的前提下继续整理内部代码。

实现验收点

  • make check 在 Pages 模块完成格式、静态检查、完整测试和构建。
  • Gitea 修改通过对应格式化、模板 lint、后端检查和目标集成测试。
  • HTTP、前置代理源站和 Pages 自管 HTTPS 都有发布确认测试。
  • DNS-01 测试覆盖 provider 选择、参数隔离、环境恢复、传播解析器和失败退避。
  • 归档测试覆盖摘要、限额、路径、相对符号链接、执行位清理和原子替换。
  • 同步测试覆盖全量分页、补查、增量游标、迟到结果和本地状态恢复。
  • 设计文档的章节验收点可以对应到代码路径或自动化测试，mdBook 能完整构建。

GitHub Pages 调研与功能评估

本章从 GitHub Pages 的公开产品能力中提取站点地址、发布来源、域名和状态展示规则，并说明它们在 Gitea Pages 中的对应设计。最终行为由各专题章节完整定义。

站点归属和默认地址

GitHub Pages 区分用户/组织主页和项目站点，项目站点使用仓库路径。GitHub Pages 概述

Gitea 采用固定 .pages 仓库提供所有者主页，普通仓库提供项目路径：

<owner>.<pages-instance>/       # <owner>/.pages
<owner>.<pages-instance>/<repo>/

每个仓库最多一个站点，默认关闭；用户和组织使用相同规则。外部地址使用当前名称，内部使用 repo_id，因此改名和转移能自然更新地址而不复制内容。固定仓库名适用于多个 Pages 实例，不需要为每台实例保存主页选择。

实现验收点

  • .pages 自动成为所有者主页，普通仓库自动成为项目站点。
  • 多个实例可以使用不同根地址，同一仓库用途保持一致。
  • 站点默认关闭，改名和转移更新外部地址但保持仓库 ID 和自定义域名。

发布来源

GitHub 支持分支目录和 Actions 构建产物。发布来源配置、自定义 Actions 工作流

Gitea 保留 GitHub 的两种自动发布方式，并增加随时可用的网页/API 上传。三种版本产生方式统一生成 TAR.GZ：

来源采用方式原因
分支目录固定提交 SHA，读取根目录或指定目录生成 TAR.GZ。无需工作流，固定提交保证一次读取一致。
Actions 成品同仓库工作流上传 Artifact，部署步骤把同一运行成品交给 Gitea。复用现有 Artifact、OIDC 和 pages: write 边界。
网页/API同步上传完整 TAR.GZ。支持外部构建系统和人工发布。

Actions 的构建命令由工作流完成，Gitea 只接收静态成品；这样构建工具与 Pages 发布链路保持分离。Action 兼容性必须在真实 Gitea URL、Runner 和版本组合上验证。上传 Pages 产物、部署 Pages 仅作为协议参考。

设置页只在“Actions 或上传”和“分支目录”之间选择自动发布方式。网页/API 上传放在版本管理页，因为它表示管理员明确选择一个新版本，不需要先切换或覆盖自动来源；分支模式下上传后，只有分支出现新提交才会再次自动产生版本。

实现验收点

  • 分支、Actions 和网页/API 上传都进入同一 TAR.GZ 检查、存储和主动部署链路。
  • 自动发布方式只有 artifact 与 branch；手动上传不会改变自动发布方式及分支处理进度。
  • 分支来源固定提交并由周期检查补偿未及时处理的变化。
  • Actions 成功表示成品已准备，实例发布结果单独展示。
  • 工作流负责构建并提供静态成品，Pages 从已生成的静态成品开始检查、保存和发布。

自定义域名与 HTTP/HTTPS

GitHub Pages 支持自定义域名、HTTPS 和证书自动维护。Gitea 将管理责任拆分：Gitea 定期检查用户域名 TXT 所有权，Pages 侧执行 ACME 和真实入口检查；用户自定义域名采用 HTTP-01，Pages 默认域名可采用 DNS-01。GitHub 自定义域名、HTTPS

Gitea 多实例允许同一域名分别在实例上成功或失败，仓库页面展示实例结果。自定义域名从根路径提供一个站点，默认地址仍使用所有者和仓库路径。

实现验收点

  • 自定义域名只绑定一个仓库并经过 TXT 所有权条件。
  • 证书材料和 ACME 请求留在 Pages，不进入 Gitea 数据库。
  • HTTP-01 预检查失败时不消耗 CA 验证请求，地址结果按实例分别展示。

仓库可见性与公开访问

GitHub Pages 的网站访问和源码仓库权限可以分开。Gitea Pages 网站使用公开访问方式：私有源码可以明确发布公开网站，公开仓库转为私有仓库时站点关闭，重新启用需要再次确认。

实现验收点

  • 管理页面明确显示源码可见性与网站公开性是两个事实。
  • 网站请求不读取 Gitea 会话或仓库权限。
  • 私有源码仓库经过明确确认后可以发布公开网站，仓库可见性变化会关闭站点。

部署状态与规模参考

GitHub 的部署结果通常表示一次成品是否成功。Gitea Pages 分开记录成品准备、内容安装、配置应用和地址发布，因为独立实例可能离线或只有某个自定义域名失败。所有实例主动部署全部站点，使用稳定时间分页、有界并发和持久当前事实处理大规模站点。

实现验收点

  • 成品准备成功不会直接显示为网站发布成功。
  • 单个实例或单个地址失败不会阻塞其他实例。
  • 大量站点使用分页、并发和周期恢复，不依赖访客请求触发部署。

通信、同步与状态展示

Pages 实例使用独立 Bearer 凭据主动连接 Gitea。通信只传输当前站点事实、当前 TAR.GZ 和实际结果；普通网站请求不访问 Gitea，也不会触发同步、下载或部署。

通信身份与接口

全局管理员登记实例时，Gitea 使用安全随机数生成 32 字节凭据，以无填充 Base64URL 交付明文，只保存 SHA-256。实例用标准 HTTP Authorization Bearer 格式提交凭据，并用 YAML 中的 pages.root_url 注册根地址；同一地址重复注册幂等，地址改变会推进实例根地址时间。凭据不放入 URL、日志或结果正文。重置凭据会推进实例根地址时间、清除该实例结果并等待新凭据首次通信；新进程即使继续使用同一地址，也会发现本地确认已过期并重新上报当前结果。

接口作用
PUT /api/internal/pages/instance注册或更新实例根地址。
GET /api/internal/pages/sites空状态实例查询全部当前站点，响应同时携带归档限额和业务 TXT 要求。
GET /api/internal/pages/sites/updated?since=...按 Gitea 时间查询当前更新，响应同时携带归档限额和业务 TXT 要求。
GET /api/internal/pages/sites/{repo-id}/content/{sha256}下载当前摘要对应的 TAR.GZ。
POST /api/internal/pages/results上报一个实例站点的当前结果。

所有接口都使用实例凭据。Gitea 在凭据通过后记录实例最近通信时间，一分钟内连续请求合并为一次数据库写入；这个时间让管理员判断凭据是否已被实例使用，同时避免站点轮询和成品下载产生高频写入。JSON 请求限制正文大小，站点查询限制每页数量，结果写入设置短超时；TAR.GZ 下载采用流式响应，避免把成品完整载入内存。实例默认每分钟轮询并加入随机偏移，启动和重新连接立即处理；轮询是唯一的同步机制，持久时间和事实负责恢复。

实现验收点

  • 每个请求通过标准 HTTP Bearer 解析和凭据摘要唯一确定实例，协议名大小写与空白按 HTTP 认证规则处理；凭据重置后旧值不能查询、下载或上报。
  • 通过凭据的任一实例请求都会在一分钟内推进最近通信时间；无效凭据不会改变该时间。
  • 根地址同值注册幂等，变化产生新的实例根地址时间。
  • 凭据重置推进实例根地址时间、清除最近通信时间和旧结果，新凭据注册同一地址后仍会重新确认全部当前站点。
  • JSON 正文、查询页大小和结果写入时间都有明确上限，TAR.GZ 使用流式下载，访客请求不进入管理通信。
  • 所有实例查询同一当前站点集合，并在本机独立部署。

当前状态同步

Pages 没有完成同步游标时执行全部查询，并在内存中建立待替换快照。Gitea 按 (pages_updated_unix_nano, repo_id) 递增分页，固定本轮 until；全部分页完成后补查 until 之后的更新。站点查询的每个响应同时携带 archive_limits 和 require_gitea_txt_record，Pages 要求同一轮所有分页返回相同值。全部分页和补查成功后，Pages 才把新快照及这组配置写入 etcd 并替换活动快照，再清理差集；查询或写入失败时当前进程继续使用上一份完整快照。

当前记录包含实例部署所需的完整事实：仓库 ID、删除与启用状态、所有者和仓库名称、当前 TAR.GZ 摘要，以及唯一的当前自定义域名和业务 TXT 结果。自定义域名为空表示站点当前没有绑定；协议使用单值是因为 Gitea 的域名替换流程始终只选择一个当前域名，正在释放的旧域名由结果确认流程管理。Pages 根据仓库名称推导主页或项目路径。来源错误只供 Gitea 管理页面使用，不增加 Pages 同步字段。删除记录保留到实例完成旧域名清理；已经释放的历史删除记录不进入新实例的全部查询。

正常运行使用 since < time <= until 的增量查询。until 由 Gitea 在第一页确定，同一轮后续页复用该值；整轮成功后 Pages 直接把这个 until 保存为下一次 since，因此协议不需要第二个含义相同的游标字段。第一页配置校验并持久化后，每页当前事实可以安排部署，后续分页配置不一致时保留原游标并重新查询。新增或变化的站点在事实落盘后立即入队；队列暂时满时通知一个后台扫描协程，扫描协程收集待处理仓库 ID，并随着工作队列释放空间持续填充。启动和每五分钟恢复扫描仍用于重新发现进程重启及部署失败留下的目标。这样执行队列始终有界，大量首次部署也不会按五分钟间隔分批停顿。初始化的全部查询和补查完成前继续使用上一份活动快照，完成后一次替换并清理差集。

archive_limits 包含压缩 TAR.GZ、展开后全部普通文件、单个普通文件和 TAR 条目数上限。Pages 将确认后的值用于后续下载和展开；配置变化只影响新的部署或重试，不主动重装已经发布且站点事实未变化的内容。require_gitea_txt_record 变化时只重新检查带自定义域名的站点，因为默认地址不依赖这项条件。

递归 DNS 地址和 TXT 刷新周期属于各进程的本机配置。Gitea 只同步是否要求业务 TXT 的布尔值，不同步 Gitea 或 Pages 的解析器地址、刷新周期和 ACME 查询解析器。这样通信事实保持稳定，也允许各实例按所在网络选择可访问的 DNS 服务。

etcd 在替换完整快照前写入“全量同步处理中”标记，快照和元数据全部写完后删除标记。进程若在持久化中途退出，下次启动忽略可能混合的新旧站点记录并重新执行全部查询；已展开的网站目录暂时保留，待完整快照确认后再清理。这个恢复过程不尝试推断中断位置，使本机路由只建立在完整的 Gitea 事实上。

实现验收点

  • 全部和增量查询按 Gitea 时间、仓库 ID 稳定分页，分页期间的更新通过补查取得；每个响应携带相同的归档限额和业务 TXT 要求。
  • 初始化的完整分页和补查成功后才替换活动快照；增量分页全部成功后才推进游标，失败时从原游标重取。
  • 完整快照持久化中断后，下次启动识别恢复标记并重新全部查询，不使用混合快照建立路由。
  • 变化站点立即入队；队列满时单一后台扫描协程随着队列释放空间持续补充，重启和失败目标由启动扫描及五分钟恢复扫描重新发现。
  • Pages 只使用 Gitea 返回的查询依据，不使用本机时间计算同步范围。
  • 每轮响应的 until 在分页期间保持固定，完整处理后直接成为下一轮 since。
  • 当前关闭、无成品和待释放域名的记录具有明确处理事实，删除清理不会依赖历史全量扫描。
  • 初始化失败不保存完成游标、不开放残缺站点；重启后可以从全部查询恢复。
  • 队列满不会丢失当前目标，后续扫描可以重新安排部署。
  • 新部署使用最近确认的归档限额；限额变化本身不重新部署已经发布的站点。
  • 同步协议只传输业务 TXT 要求，不传输各进程的解析器和刷新周期。

当前 TAR.GZ 下载

Pages 根据站点事实取得当前 SHA-256 后请求下载接口。Gitea 通过 pages_site.current_version_id 解析当前版本，验证凭据、仓库当前状态和 URL 摘要仍与该版本一致，再从现有 storage 流式返回原始 TAR.GZ 字节。Pages 不接触版本 ID、版本历史、Gitea storage 路径或后端凭据；扁平协议使 Pages 实例继续只处理当前目标。

条件响应
当前摘要匹配且对象可读200 application/gzip，正文为 TAR.GZ 原始字节。
摘要已经变化409 pages_state_changed。
站点关闭、没有成品或不存在404。
storage 暂时不可用503。

Pages 先完整写入受限临时文件，再计算 SHA-256 和执行发布章节规定的检查。摘要变化、损坏和临时存储错误都保留旧本地内容，并按有限退避重试。

实现验收点

  • 下载接口只返回站点当前版本的对象，历史版本恢复后才会成为实例下载目标。
  • Pages 下载后重新计算摘要，检查成功前不替换当前内容。
  • 查询与下载之间发生变化时实例重新查询当前事实。
  • 缺失、损坏和暂时 storage 错误显示为实例错误，不把错误正文安装为网站。

结果上报

结果请求包含实例处理的当前时间和本机事实：

  • repo_id；
  • applied_pages_updated_unix_nano；
  • applied_root_updated_unix_nano；
  • applied_require_gitea_txt_record；
  • config_applied、actual_tar_gz_sha256、default_published、custom_published 和稳定 error_code。

Gitea 在短事务中核对实例凭据、实例根地址时间和站点时间；存在当前或待释放自定义域名时，还核对实例使用的业务 TXT 要求是否等于当前配置。这使开关变化后，旧条件下的结果不能被当作当前确认。任一核对事实已变化时返回 state_changed，旧正文不能覆盖当前结果。实例声明地址已经发布时，实际摘要还必须等于站点当前摘要；旧摘要可以随失败结果上报，用来说明本机仍安装的内容，但不会被接受为当前地址已经发布。结果写入 pages_instance_site，每个实例和站点只有一份当前结果；删除站点完成域名释放后不再创建结果行。

config_applied 表示旧路由、挑战和续期已经按当前配置处理；内置发布器应用当前路由并完成本机 listener 探测后写入该确认状态，停用也要确认入口已经停止。地址发布字段表示内容、证书、TXT 和实际入口是否都成功。两者分开，使“内容已经安装但自定义域名证书失败”能够准确显示。Pages 对同一站点只保留一份未确认结果，收到明确响应后才生成下一份；连接中断则原样重试。embedded etcd 无法写入部署结果或待确认结果时，实例仍用同一接口直接报告当前失败，使仓库侧在本地磁盘故障期间也能看到实例错误；站点时间和根地址时间继续阻止迟到结果覆盖新事实。部署超时已经取消工作上下文时，失败报告使用独立且受 HTTP 客户端超时限制的请求完成上报。

实现验收点

  • 旧站点时间、根地址时间或不符合当前业务 TXT 要求的域名结果返回 state_changed，不会覆盖较新的事实。
  • 地址发布成功只接受与当前成品一致的实际摘要；旧摘要只能表达尚未完成当前发布。
  • 结果事务只进行鉴权、当前事实核对和数据库写入，不执行下载、证书或网络探测。
  • 内容安装、配置落实、默认地址发布和自定义地址发布分别可以表示。
  • 同一站点的待确认结果至多一份，重试幂等且不会让旧失败覆盖新成功。
  • 本地结果无法持久化时仍尝试上报当前失败；部署超时不会同时取消这次有界错误上报。
  • 结果正文和页面不包含凭据、私钥或存储后端信息。

仓库与全局管理页面状态

Pages 在仓库设置导航下分为“设置”和“版本”两页。设置页负责站点开关、自动发布来源和自定义域名配置，因为这些内容共同决定 Gitea 下发给实例的站点事实；版本页负责 TAR.GZ 上传和内容历史。两页分别处理发布配置与成品管理，用户修改来源时不需要在版本记录中寻找入口。

自动发布方式只有“Actions 或上传”与“分支目录”：前者可以限制 Actions 分支，后者选择分支和仓库相对目录。来源处理失败仍显示在设置表单附近，使管理员可以直接修正对应配置；自定义域名区域显示域名绑定、业务 TXT 记录和最近校验结果。

版本页沿用 Gitea 的标准表格，标题显示版本总数并提供 TAR.GZ 上传入口。版本按 ID 倒序稳定分页，表格分别显示内容摘要、首次产生方式、创建时间和操作；仍存在的 Actions 运行可以直接打开。当前版本在其所在页显示 Current 标记，并提供部署详情和删除操作；历史版本提供恢复和删除操作。部署详情使用一个服务端渲染弹窗，按 Pages 实例显示默认地址、自定义域名、发布状态和当前有效错误，不为历史版本保存或推导部署状态。恢复、上传和删除都重定向回版本页 GET，刷新页面只读取操作结果。

删除当前版本会关闭 Pages、清空当前指针并推进站点时间，使实例在同步后撤下网站；最后一个版本使用相同处理。这个行为会停止分支计划任务继续选择该站点，已经开始处理的分支或 Actions 候选也要在写入前确认站点仍启用，从而防止迟到任务重新产生当前版本。其他历史版本与域名配置继续保留，恢复版本后由用户明确重新开启站点。

自定义域名设置一次聚焦当前使用、待验证或正在释放的域名。配置要求业务 TXT 时，待验证域名显示可复制的 TXT 名称和值；替换期间原域名继续使用；释放完成前保留当前状态。Pages 实例上报的结果继续作为同步接口和 Actions 部署状态的事实来源，版本表格只表达内容版本，避免把实例运行结果误认为历史版本属性。

全局管理页使用 Gitea 标准管理表格，标题显示实例数量并提供创建入口。表格展示实例 ID、公开根地址、最近通信时间和操作：自动表格布局让 ID 按内容保持紧凑宽度，操作列只扩展到图标所需宽度，公开根地址和最近通信在中间平分剩余空间并居中显示；这种布局不会压缩 ID，也不会让操作列占用展示信息的空间。ID 用于将页面操作与日志、数据库记录对应；已经注册根地址的实例显示可访问地址；最近通信使用相对时间，悬停可以查看精确时间，尚未通信时显示 Never；末列沿用管理员列表的 Op. 标题和无边框图标操作。架构说明属于设计文档，不占用日常管理列表。

创建实例先使用 Gitea 的操作确认框说明会生成一次性凭据。创建或重置成功后，Gitea 把明文暂存在当前管理员的服务端会话，并把 POST 重定向到管理页 GET；这个 GET 以只读输入框显示一次完整令牌、提供复制按钮并立即消费会话值，运维把它写入 Pages YAML 的 gitea.token。页面刷新因此只执行 GET，不会重复创建或重置，明文也不会再次显示。Gitea 后续只保留数据库中的摘要。重置会立即废止旧凭据并把最近通信时间恢复为 Never，新实例成功使用新凭据后再写入时间。根地址更新时间继续用于同步协议的并发控制，管理页使用最近通信时间表达运维需要的连接事实。移除实例前的确认信息要求运维先停止或隔离真实入口，因为删除 Gitea 登记不会停止外部 Pages 进程。归档限额和业务 TXT 要求属于 Gitea 启动配置，管理页只展示实例登记。

Actions 部署状态仍同时表达“成品已提交”和“实际发布”。实际发布只有在所有已登记且具有 root_url 的实例确认当前摘要和默认入口成功时为 success；任一实例明确报告默认入口失败时为 failure；没有服务实例或仍有实例未完成时为 in_progress；站点关闭或摘要已不再当前时为 cancelled。仅自定义域名失败不会阻塞默认入口的成功状态。错误码映射为本地化说明，例如内容下载失败、归档无效、内容安装失败、入口应用失败、TXT 无效、证书等待、ACME 失败和入口探测失败。

workflow run 成功提交过 Pages 成品时，Actions Summary 显示 Pages 项和当前默认网站入口。这个运行标记表达成品提交事实；网站链接按当前仓库与实例根地址生成，实例实际发布状态继续在仓库 Pages 页面按当前站点结果展示。这样历史运行页面始终提供可理解的当前入口，同时不会把后来变化的当前实例结果归因到某次历史运行。

实现验收点

  • 设置页只显示站点开关、两种自动发布方式、来源错误和自定义域名配置；版本页显示上传和分页版本管理。
  • Versions 沿用 Gitea 标准表格，标题显示版本总数和上传入口，并按摘要、来源、创建时间和操作分列。
  • 版本按 ID 倒序稳定分页；当前版本在其所在页标记，Actions 首次来源在运行存在时可以打开对应运行。
  • TAR.GZ 上传在任一自动发布方式下可用，并保持当前自动来源配置。
  • 历史版本恢复经过确认并只切换当前内容；Current 与历史版本都可以确认删除，删除 Current 同时关闭站点并清空当前指针；操作后重定向到版本页 GET。
  • Current 的详情弹窗按实例展示当前默认地址、自定义域名和有效错误；旧站点时间或旧实例根地址时间不会显示为当前结果，发布成功还要求当前摘要一致。
  • 归档仓库隐藏上传、恢复和删除操作；Current 的部署详情与已有版本仍可查看。
  • 待验证域名提供可复制的 TXT 名称和值，替换和释放期间能说明当前仍然生效的域名。
  • 全局管理页显示实例总数，并以实例 ID、公开根地址、最近通信时间和紧凑操作组成表格；ID 和操作列按内容保持紧凑，公开根地址与最近通信在中间平分剩余空间并居中显示；最近通信显示相对时间并提供精确时间提示，尚未登记根地址的实例明确显示等待连接，尚未通信的凭据显示 Never。
  • 创建实例先显示 Gitea 操作确认；创建和重置的 POST 都重定向到 GET，刷新页面不会重复操作或触发浏览器的表单重提提示。
  • 管理员取得的实例凭据只在重定向后的首次 GET 显示一次完整令牌，并能直接复制到 Pages YAML；刷新后不再显示明文。
  • 管理列表用实例 ID 对应日志和数据库记录，用最近通信时间判断当前凭据是否连接过 Gitea；重置后时间清空，下一次通过认证的请求重新写入。
  • 创建实例、重置凭据和移除实例都有明确确认，移除说明真实入口需要先由运维停止或隔离。
  • Actions 成品提交与实际发布分别展示；所有有 root_url 的登记实例确认当前摘要和默认入口后才显示 success，无服务实例或尚未完成时显示 in_progress，默认入口明确失败时显示 failure，关闭或摘要不再当前时显示 cancelled。
  • Actions Summary 只在运行成功提交过 Pages 成品时显示 Pages 项；链接使用当前默认网站地址，没有实例地址时显示成品已提交。
  • workflow run 标记、部署接口轮询状态和仓库 Pages 实例结果分别表达运行提交事实、当前摘要的等待结果和当前站点实际状态。
  • 实例结果对应旧站点、旧根地址或不同业务 TXT 要求时显示发布中，不会冒充当前发布结果。
  • 普通访问错误、访问量和文件 404 不写入部署结果。

大量站点与恢复

全部查询、增量查询和结果写入都使用稳定索引、固定页大小和有限并发。单个站点失败只影响该站点；实例本地队列满时保存事实并由后台扫描协程随着队列腾出空间继续安排。Gitea 查询不返回与当前实例无关的历史删除记录，因此首次同步规模由当前站点和待释放域名决定。

Gitea 失联时 Pages 继续提供最后确认的内容，并维护本机证书、TXT 和清理工作。正常重启沿用 etcd 游标。本地状态损坏，或 Gitea 数据库恢复后现有游标已不能表示当前数据时，运维停止 Pages、清空 YAML 中 pages.data_root 指定的数据根目录并重新启动。空状态没有完成游标，因此会自然执行全部查询并重新部署；通信凭据仍然有效，不参与同步起点的判定。永久故障实例先隔离实际入口，再从 Gitea 删除登记，使域名释放条件不再等待它。

实现验收点

  • 大量站点同步使用固定上限分页，部署使用可配置并发和有界队列，单站点错误不会阻塞其他站点。
  • 轮询中断、进程重启和队列满都能通过持久当前事实恢复。
  • Gitea 失联期间已发布内容继续服务，恢复后从保存的游标或全部查询继续。
  • 清空数据根目录后实例以原通信凭据执行全部查询，无需额外的强制同步标志。
  • 永久故障实例在入口隔离后移除登记，其他实例和当前成品保持可用。

发布、TAR.GZ 存储与访问

站点保存一种自动发布方式：branch 由 Gitea 读取固定分支目录并打包，artifact 接受同仓库 Actions 成品。网页/API 上传是独立的版本操作，在两种方式下都可用。分支、Actions 和上传最终都生成一个可以直接展开为网站根目录的 TAR.GZ。TAR.GZ 只负责传输和存储，Pages 取得后在本机检查、展开和主动部署；网站访问不依赖 Gitea 或存储后端。

Gitea 使用现有 storage 抽象保存仍被版本记录引用的成品，默认可以使用本地存储，也可以使用 Gitea 已支持的其他后端。Pages 不读取后端路径或凭据，而是用实例凭据通过 Gitea 内部接口下载当前摘要。接口地址支持 HTTP 和 HTTPS，使同机、受控内网及反向代理后的部署可以使用实际可达地址；跨越不可信网络时由运维配置 HTTPS。Gitea 负责版本保留和无引用对象清理，Pages 负责本机暂存目录和已部署目录清理。

来源、版本与当前内容

每次通过检查并完整保存的不同内容形成一个仓库级版本。pages_site.current_version_id 指向当前版本，pages_version 保存摘要、首次来源和创建时间。版本按 (repo_id, tar_gz_sha256) 唯一，因此相同内容重复提交会复用版本，也不会推进站点更新时间；恢复历史版本只切换当前指针，实例协议仍然只接收一个当前摘要。

版本产生方式触发与处理
分支目录保存完整分支名和仓库目录。启用和来源变更使计划任务立即可处理，推送由最短一分钟的周期检查发现；Gitea 随后固定提交 SHA，读取目录并生成 TAR.GZ。
Actions 成品同仓库工作流生成静态目录，上传为符合约定的 Artifact；部署步骤把同一运行和同一尝试的 Artifact 交给 Gitea，Gitea 检查后创建或复用版本。
网页/API 上传仓库管理员或授权外部构建系统上传完整 TAR.GZ，Gitea 同步接收、检查、保存并创建或复用版本。

成品准备、当前版本、内容安装和地址发布分别记录。自动来源失败时继续使用已经确认的当前版本；首次没有版本时实例保持平台 404。分支候选和 Actions 成品在提交前重新核对自动发布方式及其来源事实，方式已经变化的候选不能提交。网页/API 上传是管理员或 API 调用者明确发起的当前版本操作，因此只核对仓库状态，不改变 source_type、分支配置或分支处理进度。

仓库 Pages 设置页负责站点开关、自动发布方式和自定义域名配置；版本页负责上传与历史管理。版本页沿用 Gitea 标准表格，版本按 ID 从新到旧稳定分页，每项显示可复制摘要、首次产生方式和创建时间，当前版本在其所在页标记。Actions 首次来源在运行仍存在时链接到对应 run，运行已清理时仍显示 Gitea Actions。历史项可以通过确认操作恢复或删除；恢复不改变来源配置、启用状态或域名，只推进当前站点事实并触发现有实例重新发布。

当前版本的详情操作按实例展示默认地址、自定义域名和当前部署结果。只有结果中的站点时间和实例根地址时间符合当前事实时，页面才显示该结果；自定义域名还要求结果采用当前业务 TXT 策略。地址成功同时要求实例确认当前摘要，当前部署失败时可以保留实例仍安装的旧摘要以说明实际状态。较早结果和使用旧 TXT 策略的自定义域名显示为发布中，默认地址的有效结果不受自定义域名策略切换影响。这样版本记录继续只表示内容，详情弹窗准确表达当前内容在各实例上的实际状态。Actions 部署轮询复用默认地址的同一套判断，使两个入口对当前部署给出一致结果。

所有版本都可以删除，包括当前版本和最后一个版本。删除当前版本会在同一事务中清空当前指针、关闭 Pages、推进站点更新时间并删除版本引用；实例同步后撤下网站。关闭站点使分支计划任务停止选择该仓库，已经开始处理的分支或 Actions 候选也会在提交前再次确认站点仍启用，因此不会重新生成用户刚删除的当前版本。其他历史版本和域名配置继续保留，用户可以随后恢复明确选择的版本并重新启用 Pages。系统不会自动选择一个旧版本发布，因为删除当前内容不应隐式公开另一份内容。

实现验收点

  • 分支、Actions 和网页/API 上传都形成同一种 TAR.GZ，并进入同一检查、版本、存储、下载和部署流程。
  • 每个仓库只有一个当前版本指针；相同摘要复用版本且不产生站点更新。
  • 来源失败不覆盖当前版本，首次无版本返回平台 404。
  • 站点配置与版本管理分别位于两个页面；版本按 ID 倒序分页，历史版本可以恢复和删除，当前版本可以查看实例部署详情或删除。
  • 删除当前版本会同时关闭 Pages、推进站点时间并触发实例撤下内容；最后一个版本也能删除，历史版本和域名配置按各自操作保留。
  • 详情只接受与当前站点时间和实例根地址时间匹配的实例结果，自定义域名还要求当前业务 TXT 策略，发布成功同时要求当前摘要一致；Actions 部署轮询复用默认地址判定。
  • 恢复和手动上传保持自动来源、启用状态和域名配置；分支候选与 Actions 成品在提交时重新核对自动来源。
  • 成品准备、当前版本和各实例地址发布是不同事实，页面不会把接收成功解释为网站已发布。

分支目录发布

Gitea 固定分支头的提交 SHA，按 Git 树读取仓库根目录或指定目录；指定目录直接成为 TAR.GZ 根目录，不加入所有者、仓库或分支前缀。读取过程使用有界流式处理，边读取边计算文件大小、条目数、目录深度和符号链接边界。

打包器只接收普通文件、目录和站点内安全的相对符号链接；子模块、设备文件和越界或循环链接产生来源错误。生成失败不改变当前成品。生成完成后重新取得来源配置和分支头，只有仍然匹配时才提交当前摘要；期间的新提交进入下一次处理。

相同提交且当前对象仍可读时只更新下一次检查时间，不重复生成归档。启用和来源变更会把下一次检查设为可立即处理；推送和镜像变化由最短 1 分钟的计划任务发现。每轮只处理固定数量，到期但尚未处理的来源留到下一轮。

实现验收点

  • 每次生成固定一个提交 SHA，目录根和网站根一致，缺失分支或目录给出可定位错误。
  • Git 树读取和归档生成受文件大小、条目数、深度以及任务上下文取消控制。
  • 分支头在提交前重新核对，旧提交、旧目录和旧来源不会覆盖新来源。
  • 相同提交和正确当前对象不会重复打包，分支变化能够在下一次检查处理。
  • 生成失败时旧成品和已发布网站保持不变。

Actions 成品发布

Actions 工作流负责构建静态网站并上传约定的 Artifact。Gitea 只在已认证且仍处于运行状态的 Actions 任务中接受部署请求，并核对任务所属仓库、任务权限、OIDC 声明、完整分支引用、运行 ID、提交 SHA 和运行尝试。Artifact 必须属于该任务允许读取的尝试、状态为 upload-confirmed、名称和内容结构符合约定；其他 Artifact 不能成为当前成品。

部署步骤使用 pages: write 和 id-token: write，把允许尝试中的 Artifact 和 OIDC 声明交给 Gitea。Gitea 可以兼容 upload-pages-artifact 与 deploy-pages 的协议，但可用 Action 版本必须在真实 Gitea URL、Runner 和 Gitea 版本组合上验证；兼容结果应记录实际版本，不把 GitHub 托管环境的默认保证扩展到 Gitea。

Actions 的 Artifact 输入检查和最终 TAR.GZ 检查属于同一发布流程。Artifact 的外层 ZIP 只提取约定的 artifact.tar 作为网站成品输入；Gitea 不把外层 ZIP 的其他条目当作网站文件。缺少或重复 artifact.tar、归档结构不完整时直接报告成品错误。Gitea 读取 artifact.tar 后生成 TAR.GZ，完成摘要、存储、版本创建或复用和当前指针提交，再向部署步骤返回成品已准备。网站构建命令由工作流自行负责，Pages 从构建完成的静态成品开始发布。

同一运行的尝试号用于区分重跑，任务允许读取的尝试集合决定 Artifact 输入，旧尝试的迟到 Artifact 不能绕过任务权限或来源核对。部署接口返回的是成品转换和当前摘要提交结果，不表示 Actions 任务本身或任何 Pages 实例已经完成网站发布；实例结果通过通信接口单独展示。

Gitea 在同一个数据库事务中创建或复用版本、切换当前指针，并在所属 action_run 上设置 has_pages_artifact=true。这个单调标记表示该 workflow run 至少完成过一次 Pages 成品提交，与调用接口的具体 job 无关；字段名称特意使用 artifact，避免把成品提交误解为实例已经发布成功。重跑和多个部署 job 共享同一个运行标记。Actions run 的 Summary 根据标记显示 Pages 项，并按当前仓库名称和第一个有效实例根地址推导 View current site；没有可用地址时显示成品已提交。链接始终表示仓库当前网站，因此仓库改名、转移和实例根地址变化会自然得到新地址，历史 run 也不会保存旧地址或旧内容。

运行标记属于 Actions 的执行事实。版本的 Actions 运行 ID 只记录该摘要的首次来源；后续运行提交相同摘要时复用版本，同时为后续运行设置自己的标记。Pages 实例结果仍只描述当前站点，版本记录只描述内容和首次来源。

Actions 部署结果在 Gitea 中分为“成品已提交”和“实际发布”。实际发布的 success 只在所有已登记且具有 root_url 的 Pages 实例都确认当前 TAR.GZ 摘要，并确认默认地址发布成功时产生；任一实例明确报告默认地址失败时为 failure；没有服务实例或仍有实例未完成确认时为 in_progress；站点关闭或该摘要已不再是当前摘要时为 cancelled。仅自定义域名失败不会阻塞默认地址成功，对应错误继续显示在仓库 Pages 状态中。

实现验收点

  • 只有已认证的运行中任务、匹配的 OIDC 声明、权限和允许尝试中的 upload-confirmed Artifact 才能提交。
  • 重跑严格区分尝试号，旧尝试迟到结果不能覆盖新尝试。
  • Artifact 外层 ZIP 只提取唯一的 artifact.tar；Artifact 读取、TAR.GZ 检查、存储和版本事务完成后才返回成品已准备。
  • Action 的兼容版本经过真实 Gitea URL 验证，工作流完成构建，Pages 从静态成品开始发布。
  • 部署接口的成品提交结果、Actions 任务状态和实例实际发布结果分开处理。
  • 版本接收和 workflow run 幂等标记在一个事务中完成；run Summary 显示当前网站入口，没有实例地址时显示 Pages 内容已提交。
  • 多个运行提交相同摘要时只保留一个版本，每个成功运行仍保存提交标记，版本保留首次来源。
  • run Summary 的链接由当前仓库和实例根地址推导，文案表达当前网站入口；实例发布结果继续由当前 Pages 状态展示。
  • Actions 实际发布只有在全部有 root_url 的登记实例确认当前摘要和默认入口后才为 success；无服务实例或尚未完成时为 in_progress，默认入口明确失败时为 failure，关闭或摘要不再当前时为 cancelled；自定义域名错误单独展示。

网页与 API 上传

网页使用 Gitea 会话和表单保护；API 使用现有 Gitea token，并要求调用者对目标仓库具有代码写权限。认证和权限沿用 Gitea，发布接口直接提交当前成品。

网页上传复用 Gitea 的 Dropzone 和临时上传记录。浏览器异步暂存一个 TAR.GZ 并取得 UUID，用户提交上传表单后，Gitea 从应用数据临时目录读取该 UUID 对应的文件，执行 Pages 的压缩字节限制、SHA-256 和归档结构检查，并在处理结束后消费临时记录。Dropzone 显示完成只表示文件已经暂存；表单响应“成品已准备”才表示检查、storage 保存和当前摘要提交全部成功。API 请求直接以受限流进入同一个成品提交流程。

统一临时目录让 Gitea 现有清理机制处理异常退出留下的文件。检查成功后通过 storage 抽象保存不可变对象，在短 SQL 事务中提交站点当前摘要；同步响应不等待 Pages 实例部署。

网页和 API 每次把完整 TAR.GZ 交给同一个版本提交流程。仓库还没有 Pages 记录时，第一次上传会创建 source_type=artifact 的关闭站点并保存版本；站点保持关闭，由仓库管理员明确启用。已有站点时上传直接成为当前版本，同时保留 artifact 或 branch 自动发布方式、分支目录和已处理提交。这样上传既可以用于常规成品，也可以在自动来源暂时不可用时明确选择一个可发布版本；分支只有检测到新提交才会再次覆盖该版本。输入未完整接收时清理暂存并返回错误，重新提交时重新执行权限、摘要和归档检查。

实现验收点

  • 网页会话和 API token 都按 Gitea 当前账号、token 和仓库代码写权限检查，权限变化会拒绝新的上传。
  • 网页使用 Gitea Dropzone 异步暂存一个文件，选择、进度、类型错误和移除操作与 Gitea 其他上传页面一致；表单提交消费唯一暂存 UUID。
  • 首次上传创建关闭的 artifact 站点；已有站点时上传保留自动来源配置和分支处理进度。
  • 完整接收、摘要检查、归档检查、对象保存和 SQL 当前摘要提交完成后才返回成品已准备。
  • 只有完整 storage 对象和已提交的当前版本可供实例下载；中断后的调用可以重新提交同一完整 TAR.GZ。
  • API 和网页在同步响应中确认成品已准备，实例内容安装和地址发布继续单独展示。

TAR.GZ 保存、版本保留与对象路径

Gitea 的现有 storage 抽象保存 TAR.GZ。对象由完整小写摘要和 repo_id 确定逻辑键，摘要前两段用于分散本地目录中的文件数量，例如：

<sha256[0:2]>/<sha256[2:4]>/<repo-id>/<sha256>.tar.gz

每条 pages_version 引用一个对象，pages_site.current_version_id 决定实例可以下载哪一个对象。对象路径不随仓库改名、所有者改名、转移或当前版本切换变化；站点身份由 repo_id 保持。对象完整写入并复核摘要后，Gitea 才在 SQL 事务中创建版本并切换当前指针。

MAX_VERSIONS_PER_SITE 默认保留 10 个版本。每次成功提交或恢复都在同一 SQL 事务内裁剪版本记录：当前版本始终保留，剩余名额保留 ID 最新的历史版本。用户删除版本时，先在事务中核对仓库归属；目标是当前版本时，同一事务还会清空当前指针、关闭 Pages 并推进站点时间。事务提交后再删除被裁剪或明确删除版本的对象，并在删除前重新确认没有版本引用；清理失败留下的对象由离线 storage doctor 识别。doctor 判断引用时查询全部版本，也会分别报告当前版本和历史版本缺失的对象。

实现验收点

  • 默认配置可以使用 Gitea 本地存储，其他后端复用 Gitea 已有配置。
  • 对象完整写入和摘要复核完成后才能创建版本，存储失败不会改变当前指针。
  • 对象键使用仓库 ID 和摘要，改名、转移和版本恢复不移动或复制对象。
  • 当前版本和保留历史版本的对象都被视为已引用；裁剪后失去引用的对象才进入清理。
  • 历史版本删除只移除版本引用；当前版本删除同时关闭 Pages、清空当前指针并推进站点时间；对象只在确认无引用后清理。
  • Pages 只通过鉴权接口下载当前版本，响应不暴露后端路径或凭据。
  • storage doctor 能保护全部版本引用，并区分报告当前与历史版本对象缺失。

同步提交、版本恢复、删除与保留

三种版本产生方式最终都调用同一个提交流程：

  1. 在事务外接收或生成 TAR.GZ，计算摘要并执行接收侧检查。
  2. 使用按仓库 ID 区分的 Gitea 全局锁串行处理，重新校验仓库；分支和 Actions 还重新校验站点仍启用、自动发布方式及来源特有事实。
  3. 通过 Gitea storage 保存完整对象并确认可读。
  4. 在短 SQL 事务中创建或复用版本；摘要与当前版本不同才切换 current_version_id 并推进站点时间。
  5. Actions 来源在同一事务设置运行标记；所有来源在事务中按保留数量裁剪版本记录。
  6. 事务提交后清理被裁剪版本的对象，Pages 实例在下一次轮询取得当前摘要。

相同摘要已经是当前版本时，调用保持幂等，不推进站点时间；Actions 的新运行仍在事务中取得自己的提交标记。事务返回错误时调用方可以重试完整提交，已被版本引用的对象不会作为未采用对象删除。慢的 Git、Artifact、压缩、存储和网络操作都在数据库事务外。

恢复操作取得同一仓库锁，确认仓库、站点、版本归属和对象存在后，只在事务中切换当前指针、推进站点时间并应用保留数量。已经是当前版本时恢复幂等。删除操作取得相同锁，在事务中确认目标属于该仓库；删除当前版本时同时关闭站点、清空指针并推进站点时间，删除历史版本时只删除引用，提交后再清理对象。关闭站点可以恢复或删除内容；恢复版本不会自动开启站点。归档或已经删除的仓库拒绝修改版本。API 提供分页版本列表、按版本 ID 恢复和删除，网页使用同一服务，因此权限、归属和状态检查保持一致。

实现验收点

  • 所有来源共享同一版本提交流程，Pages 离线不影响 Gitea 接收和保存版本。
  • 只有完整对象和成功 SQL 事务才会成为当前版本；相同当前摘要不推进站点时间。
  • Actions 运行标记与版本事务原子提交，同一摘要由多个运行提交时版本仍唯一。
  • 恢复只接受目标仓库仍保留且对象可读的版本，只改变当前指针和站点时间。
  • 恢复保持来源、启用状态和域名配置，关闭站点恢复后仍保持关闭。
  • 删除接受目标仓库的当前或历史版本；删除当前版本同时关闭 Pages、清空当前指针并推进站点时间，数据库提交后才清理无引用对象。
  • 当前版本和最新历史版本按配置数量保留，裁剪对象在事务提交后清理。
  • 成品准备成功不表示内容已经安装或地址已经发布。

TAR.GZ 目录与安全检查

Gitea 在接收侧检查 gzip/TAR 结构、路径、条目类型和声明资源；Pages 下载后重新计算摘要并实际展开。两端重复路径检查是为了在不同信任边界上保护 Gitea 和 Pages 本地文件系统，职责如下：

阶段检查
Gitea 接收压缩大小、gzip/TAR 完整性、UTF-8 相对路径、重复路径、文件与目录冲突、条目类型、声明大小、条目数和目录深度。
Pages 展开SHA-256、实际展开大小、文件数、深度、路径边界、目标文件系统冲突、符号链接解析、部署超时和实际磁盘写入。

Gitea 在 [pages] 配置资源边界，并在每个同步响应中把当前值交给 Pages。默认值是压缩后最多 100 MiB、展开后最多 512 MiB、单个文件最多 100 MiB、最多 10,000 个条目；新接收和新部署使用当前值，配置变化不会主动重装已发布内容。规范化路径最多 1,024 字节、目录深度最多 32 层、符号链接解析最多 32 层属于固定格式安全规则。路径按 UTF-8 规则解析为站点内相对路径，危险路径、重复路径、文件与目录冲突和目标文件系统碰撞直接产生硬错误；检查过程不修复路径、不静默改名。普通文件、目录和站点内相对符号链接可以进入部署；链接可以解析到站点根目录，也可以指向站点内尚不存在的目标，后者访问时按普通网站文件不存在返回 404。解析过程越过站点根目录、穿过已知普通文件、形成循环，或者遇到绝对链接、硬链接、设备文件和其他特殊文件时产生硬错误。普通文件执行位清除，嵌套归档按普通文件保存，不继续展开。归档必须至少包含一个普通文件，普通文件可以位于任意安全相对路径；index.html 只是静态服务器读取目录时采用的常见首页，不是成品检查条件。Gitea 在读取压缩流和展开后的 TAR 数据时都响应调用方取消，使连接中止或任务停止无需继续消耗归档处理资源。Gitea 接收成功不等于 Pages 展开成功；损坏 CRC 或实际展开超限可能只在 Pages 侧发现，此时保留旧内容并报告部署失败。

通过检查的内容先写入同一文件系统的临时目录，再改名为按摘要命名的不可变候选目录。核心把候选交给当前 Publisher；发布器确认入口应用后，核心保存当前安装摘要并清理旧目录。发布器返回硬错误时需要先恢复原有入口，核心随后删除失败候选。内置服务和外部发布器直接引用不可变候选目录。任何磁盘或发布失败都保留之前确认的内容，磁盘预检不能替代实际写入失败处理。

实现验收点

  • Gitea 和 Pages 分别执行各自阶段的 TAR.GZ 检查，任何危险路径和不支持类型都有可定位错误。
  • Pages 实际校验摘要、展开量、条目数、深度、链接和文件系统边界；不把接收成功误报为发布成功。
  • 临时展开失败不替换当前目录，旧内容继续服务；没有旧内容时返回平台 404。
  • Gitea 和 Pages 对新部署执行同一组配置资源边界；默认值为压缩 100 MiB、展开 512 MiB、单文件 100 MiB 和 10,000 条目。
  • 两端始终执行路径 1,024 字节、深度 32 层和符号链接解析 32 层的格式安全规则。
  • 站点内相对符号链接可以解析到站点根目录或尚不存在的目标；越界、循环或穿过普通文件的链接使整个归档失败。
  • Gitea 在归档正文和 TAR 尾部读取期间响应调用方取消，并保留可识别的上下文错误。
  • 只有普通文件而没有 index.html 的归档可以通过检查，目录首页缺失只影响该目录的访问结果。
  • 发布器硬错误发生时旧入口和旧内容保持有效，失败候选被清理。

主动部署与文件访问

当前摘要提交后，每个启用实例主动下载、校验和展开候选内容，再通过统一发布器应用默认地址与可选自定义域名。部署由实例启动、同步到新摘要和持久扫描驱动；失败目标留在本地当前状态中，由后续扫描继续处理。队列有界但目标事实持久保存，访客请求只读取已发布内容。

Pages 使用 repo_id 隔离目录，每个摘要目录都是已检查的不可变快照。发布器按 Host 和基础路径选择站点，再读取本地文件；访客请求不查询远端，也不创建部署任务。内置 HTTP 服务使用内存路由直接读取内容，外部发布器可以把同一个 Content 接入自己的 Go Web 服务。内置探测入口由发布器生成，不写入网站目录，因此网站文件不能伪造发布确认。内容安装、配置应用、证书/TXT 条件和实际入口分别形成结果。下载和展开失败时保留稳定旧入口与旧内容；没有旧内容时返回平台 404。

实现验收点

  • 成品提交后无需访客访问，所有启用实例主动处理当前目标。
  • 候选目录只有在完整检查后交给发布器，半成品不会被访问。
  • 候选入口应用或探测失败后关闭，失败结果不会保留候选发布标记。
  • 默认地址和自定义地址独立报告，某个地址失败不影响其他实例和地址。
  • 普通访问只使用本机状态和文件，未知 Host、关闭站点和缺失文件返回规定的 404。
  • 内置 HTTP 服务和外部发布器接收同一种已检查内容与路由归属；内置服务通过本机 listener 实际探测确认发布。
  • 内部发布探测内容由发布器直接提供，不存在于用户网站目录中。

公开访问、自定义域名与 HTTP/HTTPS

本章定义公开 Pages 的地址、请求路由、自定义域名和业务 TXT 条件。证书取得与保存见证书章节，实例同步和结果字段见通信章节。

网站访问范围

当前 Pages 只有公开访问方式。源码仓库可以是私有的，但启用后网站对所有访客公开；网站请求不读取 Gitea 登录 Cookie，也不查询仓库读取权限。公开仓库改为私有时站点自动关闭，管理员重新启用时再次确认网站公开。

实现验收点

  • 新站点默认关闭，启用操作明确说明网站公开。
  • 私有源码启用 Pages 时网站不自动继承仓库权限。
  • 网站请求不读取 Gitea 会话、不访问 Gitea，也不因首次请求创建同步任务。
  • 公开转私有会关闭站点，重新启用需要明确操作。

公开访问与请求处理

Pages 使用实际请求的 Host 和路径选择本机路由。请求不根据代理转发的 Host 或协议头推导站点；前置代理需要把原始 Host 保持到 Pages。路径规范化后始终限制在当前内容目录，安全的站点内相对符号链接也要再次检查最终目标。

默认 Host 先匹配完整项目路径段，再匹配所有者的主页；自定义 Host 直接选择唯一绑定的站点。关闭、未部署或没有完整内容的站点返回平台 404。项目路径优先于主页，关闭项目不会通过主页同名目录读取项目文件。

GET 和 HEAD 提供静态内容，其他方法返回 405。项目路径缺少末尾斜杠时返回保留查询串的 308；目录存在 index.html 时读取该文件，不提供目录列表。归档不要求首页文件，因此没有 index.html 的目录返回 404，归档中的普通文件仍可按完整路径访问。未知 Host 返回普通 404；磁盘故障返回 503。站点可以提供自己的 404.html，没有时使用平台错误页。

当前内容目录是已经检查的不可变快照。发布器确认新入口后，核心才保存当前摘要并清理旧快照。路由键包含规范 Host、基础路径和仓库 ID，旧仓库清理只处理仍属于自己的键；同名新仓库不会被迟到清理撤销。

公开内容发送 X-Content-Type-Options: nosniff 和重新验证缓存头，平台错误使用 no-store。HTTP、前置代理源站和 Pages 自管 HTTPS 使用一致的路径边界和 404 语义。

实现验收点

  • 请求只使用本机路由和文件，首次访问不会触发同步、下载或展开。
  • 项目完整路径优先匹配，关闭项目不会从主页同名目录读取内容。
  • 路由和目录同时核对仓库 ID，改名、转移和同名仓库重建不会误删新入口。
  • 路径、符号链接和发布器使用的内容引用都限制在站点目录，半成品不可访问。
  • GET/HEAD、斜杠规范、平台 404、网站 404 和 503 具有明确行为。
  • 没有 index.html 的网站仍可发布并访问实际文件，目录请求返回 404。

默认地址与主页

默认地址采用 GitHub Pages 的外部形式。实例登记一个根地址，地址由当前所有者和仓库名称计算：

仓库地址

.pages 按当前 LowerName 自动成为主页，不保存额外主页标记。普通仓库路径为 /<repo-lower-name>/。改名、所有者改名和实际转移立即更新外部路由；仓库 ID、TAR.GZ、本机目录和自定义域名继续属于同一站点。

所有者标签按 Gitea 名称规则转换为合法 DNS 标签，编码必须可逆且避免名称碰撞；仓库名作为单个 URL 路径段。完整 Host 超过 DNS 限制时只报告该站点默认地址错误，仓库改名和自定义域名仍可继续。

默认域名与 Gitea 管理域的命名空间由实例登记时检查。部署者需要注意共享可注册父域可能共享浏览器 Cookie 和 SameSite 信任范围；需要隔离时使用独立可注册域名。这个部署风险不改变站点路由规则。

实现验收点

  • .pages 提供所有者根路径，普通仓库提供项目路径，用户和组织规则一致。
  • 同一站点在每个实例使用该实例自己的协议和域名。
  • 改名、转移和所有者改名更新外部地址，但不创建第二份站点内容。
  • 名称转换可重复、可逆且无碰撞；完整 Host 超限有明确错误。
  • 实例登记保护 Gitea 管理 Host、实例默认域名和其生成的命名空间。

名称规范化与内部身份

所有者地址使用 LowerName。合法 DNS 标签保持可读；点号、下划线和可能造成编码歧义的名称使用固定可逆编码，并保证结果满足单标签 63 字节限制。显示名称不参与地址计算。

仓库 ID 用于 Pages 目录、状态和清理；当前名称只用于外部 Host 和 URL 路径。网站文件路径保持大小写敏感，仓库路径段按 Gitea 的小写名称匹配。

实现验收点

  • a-b、a.b、a_b 和保留编码前缀名称得到不同地址。
  • 名称按 LowerName 处理，显示昵称不会改变地址。
  • 地址超限只影响对应默认地址并产生稳定错误码。
  • Pages 使用仓库 ID 关联目录和结果，名称变化不会复制或混淆内容。

自定义域名

自定义 Host 绑定一个仓库 ID，从 / 提供该站点。主页的自定义域名只提供主页仓库内容，不继承到其他项目。输入按 IDNA 查询规则转换为实际 DNS 使用的 ASCII 小写名称，同时检查单个标签和完整名称的 DNS 长度；只接受至少包含两个标签的域名，末尾根点、协议、端口、路径、IP 和通配符返回字段错误。这样 Unicode 输入、DNS 查询和 Pages 路由使用同一个名称，也不会因为隐式改写产生重复绑定或证书名称差异。

规范化 Host 在 Gitea 全局唯一，待验证、当前使用和正在释放的绑定都占用名称。Gitea 管理 Host、实例默认域名及其父子域关系受平台命名空间保护。一个站点同时只有一个当前绑定，以及一次待验证或释放操作；操作未完成时返回明确忙碌错误。

申请先进入 pending，TXT 成功或全局业务 TXT 关闭后成为 active。解绑或替换进入 releasing，只有已登记实例都确认旧入口撤销后才释放 Host。未授权申请在 24 小时后释放占用。路由安全释放以入口、挑战和 ACME 维护停止为准；运维只读证书由运维维护。

实现验收点

  • 自定义 Host 按 IDNA 查询规则规范化后全局唯一，标签和完整名称满足 DNS 长度，并拒绝单标签名称、末尾根点、协议、端口、路径、IP 和通配符。
  • 自定义 Host 从根路径提供一个站点，主页绑定不覆盖项目站点。
  • 一次域名操作完成前，新的替换或释放请求有明确结果。
  • 未授权申请在 24 小时后释放，已授权 Host 等待实例确认入口撤销。
  • 已成功域名的 TXT 查询失败先进入 24 小时宽限，到期仍失败才关闭入口；绑定归属始终保留，恢复后不会发生域名竞争。

业务 TXT 校验与全局配置

Gitea 为每个自定义 Host 生成随机 TXT 值，要求 _gitea-pages.<host> 返回该值。Gitea 的计划任务和 Pages 的本机维护循环各自使用可配置周期，默认都是 15 分钟，允许范围为 1 分钟到 24 小时。Gitea 每次实际查询都保存最近校验时间，并在仓库设置页显示该时间；新绑定在第一次查询前显示等待校验。

首次成功前，值不匹配、NXDOMAIN 和临时解析错误都不能激活域名。成功后两端分别保留自己的最近成功时间；后续任何查询失败都在该成功时间后的 24 小时内继续认可现有入口，超过 24 小时仍未恢复才关闭本端发布条件。这个宽限期使短暂 DNS 故障不会立即中断已经发布的网站，同时仍要求长期失效的域名重新证明所有权。查询恢复成功会刷新最近成功时间并重新开放已关闭的入口。

Gitea 的 [pages] DNS_RESOLVER 只用于 Gitea 业务 TXT 查询。Pages YAML 的 domains.resolver 只用于该实例的业务 TXT 查询；两者为空时使用所在系统的解析器。解析器地址和刷新周期是各进程的部署配置，不经同步接口传输，因此不同网络中的实例可以使用各自能够访问的递归 DNS。

全局管理员通过 app.ini 的 [pages] REQUIRE_GITEA_TXT_RECORD 统一设置这项要求。值为 false 时，Gitea 激活待处理域名，Pages 跳过本机业务 TXT 条件；值恢复为 true 时，Pages 清除旧的本机 TXT 检查缓存并重新检查带自定义域名的站点。每次站点查询响应都携带当前要求，Pages 确认同一轮分页取值一致后保存并应用。关闭业务 TXT 不改变证书终止方需要完成的 CA 域名控制验证。

实现验收点

  • Gitea 和 Pages 分别按自己的解析器和刷新周期执行 TXT 查询，默认周期为 15 分钟。
  • 每次 Gitea 查询都更新最近校验时间；首次查询前和已经查询过的状态在仓库页面可以区分。
  • 从未成功的域名不能激活；已经成功的域名在任一类查询失败后的 24 小时内继续发布，到期仍失败才关闭对应入口。
  • Gitea 启动配置同时作用于两端，每次同步响应携带当前布尔值，分页中的值必须一致。
  • 业务 TXT 不取代证书终止方向 CA 完成的域名控制验证。
  • DNS 临时错误和明确不匹配有稳定状态，最近成功时间在失败时保留，恢复后刷新并重新开放入口。

HTTPS 与内容开放条件

disabled 模式直接提供 HTTP。proxy 模式向 Gitea 登记 HTTPS 地址，但 Pages 只提供并确认本机 HTTP 源站，外部 TLS 和转发健康由前置代理负责。pages 模式由 Pages 终止 TLS；自定义域名必须同时满足当前内容、路由、业务 TXT、有效证书和本机 TLS/SNI/Host/路径探测，默认地址需要内容、路由和默认证书条件。某个实例或自定义域名失败不影响其他地址。

Pages 自管 HTTPS 时，HTTP-01 挑战路径由 Pages 单独管理，直接返回准确正文，不从网站目录读取。已知 Host 的普通 HTTP 请求跳转 HTTPS，挑战路径不跳转。实例根域的固定平台探测用于确认内置服务可用，网站文件不能覆盖平台路径。HTTP 与前置代理模式按本机 HTTP 行为直接处理请求。

每次发布都先把候选路由放入内置服务，再使用本机 listener、真实 Host 和专用探测路径核对仓库 ID 与成品摘要。pages 模式同时核验证书名称和有效期；proxy 模式通过 HTTP 源站核对内容和路由。探测成功后才保存当前安装摘要和地址发布状态。

实现验收点

  • HTTP 和代理源站在内容与路由实际生效后确认；Pages 自管 HTTPS 还要求证书和 TLS 探测。
  • 默认地址、自定义地址和不同实例的结果分别记录。
  • HTTP-01 挑战直接返回正文，不依赖网站目录或未签发证书。
  • 每种模式都通过自己直接控制的本机 listener 核对 Host、仓库 ID 和成品摘要后才报告发布成功。
  • Gitea 显示稳定错误原因，证书材料和 ACME 执行细节留在 Pages。

域名变更与解绑

新 Host 授权前旧 Host 保持当前状态。新 Host 成为 active 后，Gitea 在一个事务中切换站点当前绑定并把旧 Host 设为 releasing。Pages 取得新状态后按仓库 ID 清理多出的旧路由、挑战和续期，再应用新 Host；新 Host 失败不会恢复旧 Host，默认地址继续独立工作。

Gitea 使用站点当前时间和每个实例根地址时间判断旧 Host 是否已经从配置中移除。所有登记实例都确认 config_applied=true 后释放；永久故障实例由管理员先隔离入口，再移除登记。释放依赖入口、挑战和 ACME 维护停止；Pages 清理自己的 ACME 材料，运维只读证书由运维维护，不参与域名释放条件。

实现验收点

  • 域名切换在一个事务中更新当前绑定和站点时间。
  • 每个实例按仓库 ID 撤销旧入口，并分别报告配置落实和新地址结果。
  • 新 Host 失败时旧 Host 不恢复，默认地址不受影响。
  • Gitea 只在当前实例都确认旧入口撤销，或故障实例已隔离并移除后释放旧 Host。
  • 本机残留清理按绑定 ID 进行，不会重新开放已释放的 Host。

证书管理与部署

证书运行由选择 server.https.mode: pages 的 Pages 实例负责。Pages 保存 ACME 账户、证书、私钥和失败后的重试状态；Gitea 只保存自定义域名、业务 TXT 结果和实例最终发布状态。这样 Gitea 失联时，已经运行的实例仍能维护和使用本机证书。

disabled 以 HTTP 提供网站，proxy 由前置代理终止 TLS，这两种模式都不初始化证书或 ACME。责任边界由一个配置字段确定，启动和结果上报不会同时依赖两套证书状态。

ACME 实现与证书范围

所有 ACME 操作使用 github.com/go-acme/lego/v5。Pages 在内嵌 etcd 中保存 ACME 账户密钥、账户 URI、当前证书和失败重试时间。EAB 从 YAML 读取，ACME 订单和挑战只在当前操作期间存在，恢复时根据已保存证书开始新的维护操作。

默认域名证书包含实例根域和一级通配符，使用 DNS-01。用户自定义域名只申请对应 Host，使用 HTTP-01，因为实例能够直接提供该 Host 的挑战响应，而不需要取得用户 DNS 服务商凭据。业务 TXT 是 Gitea Pages 的所有权条件，CA 的 DNS-01 或 HTTP-01 是证书签发条件，两者独立判断。

多个 Pages 实例会分别为同一个自定义域名执行 HTTP-01。各实例只能确认自己配置的入口；无法通过预检查的实例保持该地址未发布并向 Gitea 报告错误，其他实例的默认地址和发布结果不受影响。

实现验收点

  • ACME 请求由 lego 完成，账户、证书和重试时间保存在内嵌 etcd。
  • 默认域名证书覆盖根域和一级通配符，并使用 DNS-01。
  • 用户自定义域名只使用 HTTP-01，并只申请当前 Host。
  • 业务 TXT 关闭时只跳过平台所有权检查，CA 验证仍按证书流程执行。
  • disabled 和 proxy 不创建证书管理器，不执行 ACME、HTTP-01 或 DNS-01。

证书来源与本地保存

Pages 自管 HTTPS 时可以使用运维提供的证书、ACME 证书或两者组合。证书进入当前 TLS 视图前检查 PEM、证书链、有效期、Host 覆盖和私钥匹配。当前证书保存在 etcd；运行时 TLS 配置从这份状态提供 SNI 证书。

可选的 server.https.certificate_root 让运维提供只读证书。默认证书位于 default/fullchain.pem 和 default/privkey.pem；自定义 Host 位于 hosts/<sha256(host)>/，其中 host 文件保存小写域名，旁边保存 fullchain.pem 与 privkey.pem。Pages 启动时读取并校验这些文件，再更新 etcd 中的当前运维证书。目录与 Pages 数据根目录分离，使网站内容清理不会修改运维输入。

运维负责替换文件证书，并通过重启 Pages 载入新的文件。ACME 证书由 Pages 在接近到期时更新。一次续期失败会保留仍在有效期内的当前证书；当前证书过期或名称不匹配时，对应 HTTPS 地址保持未发布并上报错误。

实现验收点

  • 运维证书和 ACME 证书都验证 PEM、Host、有效期和私钥匹配。
  • 运维证书目录按默认证书和 Host 摘要目录读取，合法内容同步为 etcd 当前证书。
  • ACME 证书由 Pages 续期，运维证书在更新文件并重启后重新载入。
  • 新证书校验或保存失败时，仍有效的旧证书继续提供服务。
  • TLS 按 SNI 选择默认域名或自定义 Host 证书，未知且没有证书的 SNI 握手失败。

自定义域名 HTTP-01

业务 TXT 条件满足后，Pages 才为自定义 Host 准备证书。向 CA 创建验证前，Pages 安装临时挑战正文，并逐个访问 server.https.acme.http01.probe_addresses。请求保留真实 Host，不使用系统代理，不跟随跳转，只有得到 200 和准确正文才继续。这个预检查避免已知不可达的入口反复消耗 CA 限额。

lego 取得实际挑战后，Pages 安装对应 key authorization，使用相同规则再次检查，再通知 CA 验证。挑战路径由 Pages 的 HTTP listener 直接响应，不从网站目录读取，也不依赖尚未签发的 HTTPS 证书。

签发完成后检查 Host、私钥和有效期，保存证书，再通过本机 HTTPS listener 使用真实 Host、SNI 和网站探测路径确认入口。证书已经保存与网站已经发布是两个状态，只有后者会把地址报告为成功。

实现验收点

  • CA 操作前和通知 CA 前都会访问全部预检查地址，保留真实 Host，拒绝跳转和正文差异。
  • 预检查失败时不继续 CA 验证，并向 Gitea 报告该实例的 ACME 失败。
  • HTTP-01 路径由 Pages 直接响应，上传的网站文件不能覆盖挑战正文。
  • 多实例分别完成自己的预检查和签发，并分别报告成功或失败。
  • 证书保存后还要通过本机 TLS、SNI、Host 和网站路径探测才确认地址发布。

默认域名 DNS-01

Pages 从 server.https.acme.dns01.provider 读取 lego 服务商代码，从 parameters 读取该服务商文档定义的字符串参数。参数名直接沿用 lego 约定，使 Cloudflare、Route53、阿里云和其他服务商共用同一个 YAML 结构，各服务商的认证和 DNS 接口由 lego provider 负责。参数名带 _FILE 时由 lego 从指定文件读取值，便于把凭据放在独立的只读机密文件中。

Pages 在启动同步和监听器前构造一次 provider，构造期间临时应用 YAML 参数，完成后恢复进程原有环境。后续签发与续期复用这个 provider，并直接交给 lego，因而保留服务商自带的传播等待时间、轮询间隔和顺序处理方式。一个 Pages 实例只配置一个 provider，因为 DNS-01 只维护该实例根域与一级通配符；不同实例可以各自使用不同服务商。自定义接入使用 lego 的 exec provider，通过 EXEC_PATH 指定程序。

lego 在正常订单中使用同一 provider 创建并清理 TXT。进程在挑战期间异常结束时，DNS 中可能留下旧 TXT；下一次签发创建当前挑战并继续工作，旧值由运维按 DNS 服务商记录清理。服务商私有记录 ID 保持在 provider 的当前运行生命周期内，etcd 保存可跨 provider 使用的 ACME 账户、证书和重试状态。取得证书后验证根域、通配符、私钥和有效期，再更新 TLS 视图。实例根地址变化后，证书维护使用新的根域。

lego 使用 server.https.acme.dns01.resolver 完成权威区发现和传播检查；该字段为空时继承 domains.resolver，两者都为空时使用系统解析器。标准构建包含 lego provider 注册表；需要缩小依赖和二进制的自定义构建可以使用 lego 官方的 lego_dnslight 与 lego_dns_<code> 标签，选择未编入的 provider 会在启动时返回明确错误。

实现验收点

  • 默认域名申请同时包含实例根域和一级通配符。
  • YAML 可以选择 lego provider，并按该 provider 的参数名传入字符串或 _FILE 文件路径。
  • provider 在服务启动前构造一次，参数应用结束后恢复原有环境，签发和续期复用同一实例。
  • lego 直接取得 provider，服务商的传播等待和顺序处理能力保持有效，正常订单完成后清理挑战 TXT。
  • 不同 Pages 实例可以配置不同 provider，自定义程序通过 lego exec provider 接入。
  • lego 的传播查询使用 ACME 专用解析器，空值继承业务 TXT 解析器。
  • 根地址变化后只使用覆盖新域名的证书确认入口。

维护、解绑与故障

Pages 每小时检查默认证书与已启用自定义 Host 的续期需要。失败退避保存在 etcd，重启不会立即重复请求。当前证书仍有效时续期失败不关闭网站；证书失效且没有替代证书时，只有对应 HTTPS 地址保持未发布。

站点关闭、删除或自定义域名解绑时，发布流程先移除入口，再停止该 Host 的证书维护。ACME 取得且不再使用的自定义证书由本机清理；运维证书仍由运维管理。恢复同步后，证书维护从当前启用站点集合重新推导需要保留和续期的 Host。

实现验收点

  • 证书维护在 Pages 本机执行，不增加 Gitea 计划任务或证书表。
  • 失败退避持久化，当前有效证书不会因一次续期失败被替换或关闭。
  • 关闭、删除或解绑先撤销入口，再停止相关 Host 的 ACME 维护。
  • 不再使用的 ACME 自定义证书会清理，运维证书仍由运维维护。
  • Gitea 恢复连接后，证书和入口按当前站点事实重新核对并上报结果。

实例与站点生命周期

本章定义 Gitea 当前事实如何变化，以及 Pages 实例如何按当前事实收敛。实例结果表示当前状态；发布和通信的字段含义分别见发布章节和通信章节。

实例登记与移除

全局管理员登记 Pages 实例并注入实例凭据和根地址。Gitea 校验根地址格式、管理域冲突、实例默认域名命名空间以及证书和 DNS-01 所需的派生名称，再保存实例。实例注册成功后主动查询全部当前状态并部署所有启用站点。

每个实例独立运行在一台机器上，使用自己的单成员内嵌 etcd、数据根目录和 HTTPS 责任模式。Gitea 不为站点选择某台实例；所有实例都处理同一站点集合。管理员移除实例前先隔离其实际入口，随后即可删除登记；这使域名释放和删除清理继续依赖仍登记实例的确认。

移除可以是最后一个登记实例。管理员完成入口隔离后即可执行，不增加全局 Pages 停用状态；已经进入 releasing 的域名由 Gitea 按现有释放事实继续完成释放，最后实例移除不会让待释放域名永久保留。

实现验收点

  • 新实例只在根地址和命名空间检查通过后参与同步和域名释放条件。
  • 实例注册幂等，根地址变化产生新的实例时间并要求本地重新应用。
  • 所有实例主动处理全部启用站点，不保存单实例部署选择。
  • 管理员先隔离入口后可以移除最后实例；移除后不增加全局停用状态，待释放域名继续完成释放。

站点创建、启用与来源

仓库首次保存 Pages 设置或首次上传成品时创建一条 pages_site，默认 enabled=false。首次上传自动选择 artifact 发布方式；设置页面可以选择“Actions 或上传”与“分支目录”两种自动发布方式。网页/API 上传属于版本操作，在任一方式下都可以把经过检查的 TAR.GZ 设为当前版本，同时保留自动发布配置。这样管理员可以紧急发布一个明确版本，分支后续只有出现新提交时才继续自动更新。

启用时 Gitea 检查来源配置和仓库状态，推进站点更新时间。没有当前成品时可以保存启用意图，但实例保持平台 404，直到成品准备完成。来源失败只更新来源错误，不覆盖当前成品；来源切换时旧候选失效，实例按最新当前事实处理。

实现验收点

  • 每个仓库最多一条站点记录，首次设置或上传创建后默认关闭。
  • 启用、关闭、来源变更和当前版本变化推进站点时间；相同当前摘要的重复提交保持时间不变。
  • 启用无成品时实例返回平台 404；成品准备成功后主动部署。
  • 来源错误、当前版本和实例结果相互独立。
  • 手动上传在任一自动发布方式下都可用，并保持来源配置和分支处理进度。

关闭、重新启用与删除

关闭站点时 Gitea 设置 enabled=false 并推进站点时间。Pages 撤销站点路由；HTTPS 实例同时停止该站点的自定义域名挑战和续期。Gitea 保留当前成品和域名管理事实，页面显示实例配置是否已经落实。重新启用只处理最后当前状态，快速关闭再启用不会要求完成一个已经被新状态取代的中间状态。

删除仓库沿用仓库工作锁和删除事务，把站点压缩为永久删除记录：保留 repo_id、删除标记和更新时间，清空来源、来源错误和当前版本指针；同一事务删除该仓库全部版本引用，并把摘要列表交给事务后的 storage 清理。这样仓库事务回滚时对象仍有引用，提交成功后又能一次清理当前和历史版本。实例收到删除记录后先撤销路由、挑战和续期，再清理目录并上报配置落实。待释放域名由实例确认后释放；Pages 本机物理文件清理由实例继续重试。

关闭或删除后的旧目录不能被同名新仓库复用。路由和清理都核对 repo_id，新仓库使用新的 ID。

实现验收点

  • 关闭状态停止站点入口并停止对应证书/挑战维护，当前成品仍可由管理面查询。
  • 重新启用处理最后当前状态，页面不会虚构中间关闭已全部完成。
  • 删除事务保留精简 repo_id 记录，在事务内清除全部版本引用，并在提交后清理 Gitea storage 对象。
  • 待验证域名可以直接释放，已授权域名进入 releasing 并等待实例确认。
  • 同名新仓库的路由、目录和启用标记不会被旧删除清理影响。

仓库归档、改名、转移与新仓库派生

仓库改名、所有者改名和实际转移只改变外部地址和路由，推进站点更新时间；仓库 ID、当前及历史版本、本机目录和自定义域名绑定继续属于原站点。.pages 用途按当前仓库名自动变化，改为 .pages 成为主页，改离 .pages 成为项目站点。

Pages 按仓库 ID 撤销当前配置中不存在的旧路由，再建立新路由；网站文件不由 Gitea 改写，绝对地址由来源构建流程负责。待验证和已授权的自定义域名绑定都随站点 ID 保留，转移只更新站点归属和路由事实。

仓库归档会关闭 Pages 站点并推进站点时间，解档后也保持关闭，管理员需要明确重新启用；已经保存的成品和域名事实按关闭流程保留。派生、模板生成、外部导入和收养 Git 仓库创建新的仓库 ID，Pages 默认关闭且不复制来源、成品、域名或结果。镜像同步保留原 ID，只触发分支来源重新检查。

实现验收点

  • 改名和实际转移推进站点时间并更新地址，内容和已授权域名保持关联。
  • .pages 用途完全由当前名称推导，显示昵称和转移申请不改变地址。
  • 旧路由清理按仓库 ID 进行，不能撤销同名新仓库。
  • 待验证和已授权域名都随站点 ID 转移，转移后的当前站点继续使用同一绑定事实。
  • 归档会关闭 Pages，解档后仍保持关闭，管理员明确重新启用后才恢复发布；派生和导入仓库获得新 ID、默认关闭且不复制 Pages 数据。

自定义域名变更与释放

新 Host 通过 TXT 授权后，Gitea 在一个事务中把它设为当前绑定、把旧 Host 设为 releasing 并推进站点时间。Pages 取得新状态后按仓库 ID 撤销旧路由、挑战和续期，再应用新 Host；新 Host 失败不会恢复旧 Host，默认地址继续独立服务。

旧 Host 释放要求每个已登记实例在当前站点时间和当前根地址时间下报告 config_applied=true。新登记实例完成全部查询、刚改根地址的实例完成重新应用前都参与条件。永久故障实例由运维先隔离实际入口，再移除登记。释放只确认入口已撤销，证书和文件残留由 Pages 按绑定 ID 继续清理。

实现验收点

  • 域名切换原子更新当前绑定、释放旧绑定并推进站点时间。
  • 每个实例按仓库 ID 清理旧绑定，并分别报告配置落实和新地址结果。
  • 旧 Host 释放不会等待物理文件删除，但必须确认入口、挑战和续期已停止。
  • 新实例、改址实例和永久故障实例分别按当前状态进入或退出释放条件。
  • 清理按绑定 ID 进行，不会重新开放已经释放的 Host。

失联、重建与永久故障

Gitea 暂时失联时，Pages 使用最后确认的本机状态继续提供公开网站，并继续本机 TXT、证书和清理维护。内置 Web 服务随 Pages 进程停止；使用前置代理时，代理本身仍可运行，但源站不可用。恢复后从 etcd 游标继续同步并重新核对当前条件。

本地 etcd 无法读取、游标超前或 Gitea 数据库恢复后现有游标已不能表示当前数据时，运维停止 Pages、清空 YAML 中 pages.data_root 指定的数据根目录，再使用原有实例凭据启动。空状态从首次全部查询、补查和主动部署开始，通信凭据仅表示实例身份，不影响同步起点。

失联期间同名新仓库可以暂时命中旧内容；恢复同步后先按旧 repo_id 撤销旧路由，新仓库部署成功后再开放相同外部路径，否则返回平台 404。永久故障实例先隔离真实入口，再从 Gitea 移除登记，其他实例和当前成品不受影响。

实现验收点

  • Gitea 失联时已确认网站继续服务，Pages 本机证书和 TXT 维护不依赖管理请求。
  • Gitea 失联与 Pages 进程停止是两种状态：前者继续使用本机确认内容，后者停止内置源站。
  • 状态损坏、游标超前和数据库恢复都通过清空本机数据根目录触发首次全部查询，实例凭据保持不变。
  • 清空目录后从空配置开始，按 Gitea 返回的时间和仓库 ID 顺序重建，未部署站点返回平台 404。
  • 永久故障实例先隔离入口再移除登记，其他实例和 Gitea 当前成品保持可用。

Gitea 数据表

Gitea 使用五张 Pages 业务表。站点表保存当前配置和当前版本指针，版本表保存可恢复的内容事实，实例结果表继续只保存每个实例的最后结果。内容历史与部署结果采用不同生命周期：恢复内容需要版本历史，而仓库页面判断当前是否发布只需要最后结果。

pages_site

相同内容再次提交时复用原版本，因此首次来源保持稳定。Actions 的另一次运行提交相同内容时仍会记录该运行的提交标记，但不会复制版本。[pages] MAX_VERSIONS_PER_SITE 控制每个站点保留数量，默认 10，允许 1 到 100；每次成功提交或恢复时保留当前版本和其余最新版本，并在数据库事务提交后清理失去引用的对象。用户可以删除任意版本；删除当前版本的事务同时清空当前指针、关闭 Pages 并推进站点更新时间，删除历史版本只移除版本引用。提交后才清理无引用对象。同步裁剪使配置降低后在下一次内容操作自然生效，不需要计划任务。

pages_instance

每行对应一个全局管理员登记的 Pages 实例。

字段含义
id实例 ID。

last_communication_unix当前凭据最近一次通过认证访问 Gitea 的时间；0 表示尚未通信。

证书、DNS、数据目录和 HTTPS 责任模式属于 Pages 本机配置，不进入 Gitea 表。

pages_domain

每行对应一个自定义域名绑定。host 规范化后全局唯一；业务 TXT 结果由 Gitea 维护，Pages 进行本机复查。

字段含义

created_unix_nano创建时间。

ACME 账户、证书、私钥和 DNS 服务商凭据由 Pages 本机管理。

pages_instance_site

每行保存一个实例对一个站点最后一次被 Gitea 接受的结果。这个表用于判断当前网站状态，新的结果覆盖同一实例和站点的旧结果。

Go 模型在 models/pages 中命名为 InstanceResult，表名继续使用 pages_instance_site。类型名称表达它是实例的当前部署结果，固定表名则让迁移、查询和设计字段保持一致。

Gitea 接收结果时通过 current_version_id 解析当前摘要，并核对站点时间、实例根地址时间和适用的业务 TXT 要求。旧结果返回 state_changed，使较早部署的结果不会覆盖当前状态。

Actions 运行标记

现有 action_run 表增加 has_pages_artifact 布尔字段。Actions 成品接收时，版本创建或复用、当前指针切换和运行标记在同一个数据库事务完成。字段名称表达“该运行提交过 Pages 成品”，因为实例发布成功属于独立结果；这样接口成功时版本与运行标记一定同时可见，事务失败时两者都不生效。

标记表示该 workflow run 至少成功提交过一次 Pages 内容。相同摘要由多个运行提交时只产生一个版本，但每个成功运行都有自己的标记。版本只记录首次 Actions 来源，当前地址仍由实例根地址和仓库名称推导，当前发布结果仍由 pages_instance_site 推导，因此 Actions 表无需复制站点状态。

实现验收点

  • 数据库包含 pages_site、pages_version、pages_instance、pages_domain 和 pages_instance_site 五张 Pages 业务表。
  • 站点使用 current_version_id 指向当前内容；版本表按仓库和摘要唯一，并只保存版本身份、首次来源和创建时间。
  • 相同内容重复提交复用版本；不同 Actions 运行提交相同内容时都保存运行标记，版本首次来源保持不变。
  • Actions 运行标记、版本创建或复用和当前指针切换在一个事务中提交。
  • 每次内容提交或恢复后保留当前版本和配置数量内的最新历史版本；对象只在版本引用删除后清理。
  • 任意版本都可以删除；删除当前版本同时关闭 Pages、清空当前指针并推进站点时间，删除事务提交后只清理已经没有版本引用的对象。
  • 删除仓库保留精简站点记录，清除该仓库全部版本引用，同名新仓库使用新 repo_id。
  • 自定义域名表只保存业务 TXT 管理事实，ACME 材料保存在 Pages 实例。
  • 实例最近通信时间由通过认证的内部接口请求更新，一分钟内连续请求合并写入；重置凭据后恢复为尚未通信。
  • 实例结果按站点和实例保存一份，站点时间、根地址时间和适用的业务 TXT 要求共同确认该结果属于当前事实。

Gitea 时间与查询

Gitea 为站点和实例根地址生成更新时间。归档限额和业务 TXT 要求来自启动时加载的 app.ini，每个站点查询响应都直接返回当前值；这些配置独立于站点分页游标。Pages 使用 Gitea 返回的站点时间和根地址时间作为查询依据，不用本机时钟计算同步范围。

首次同步按 (pages_updated_unix_nano, repo_id) 递增分页，并固定本轮 until。Pages 在内存中收集结果，并确认全部分页和补查返回相同的归档限额与业务 TXT 要求；全部成功后才一次持久化并替换本机活动快照。持久化前写入恢复标记，站点和元数据完整写入后清除；进程在这段时间退出时，下次启动忽略未完成快照并重新全部查询。正常运行使用 since < time <= until 的增量查询，第一页确认配置，后续分页必须保持一致，分页失败时保留上一轮查询依据。查询依据大于 Gitea 当前范围时返回 pages_cursor_ahead，运维按生命周期清理本机状态后重新全部同步。

实现验收点

  • 首次和增量查询都按站点时间、仓库 ID 稳定分页；每轮分页使用一致的归档限额和业务 TXT 要求。
  • 全量分页和补查都成功后才替换活动快照，分页期间的更新不会遗漏。
  • 全量同步失败时继续使用上一份快照，成功后一次清理快照差集。
  • 全量快照持久化中断时保留恢复标记，重启后重新全部查询并在完成前关闭未确认路由。
  • 查询依据损坏能通过清空本机数据后重新初始化，时区或本机时间变化不会造成遗漏。

Pages 本地状态与主动部署

Pages 使用 go.etcd.io/etcd/server/v3/embed 启动独立单成员 etcd。客户端、Peer 和指标服务只在进程内使用，不绑定外部端口。YAML 中的 pages.data_root 指定唯一数据根目录，进程锁保证同一目录只有一个 Pages 进程。

etcd 保存 Gitea 查询游标、最近确认的归档限额和业务 TXT 要求、当前站点事实、实际安装摘要、地址开放状态、证书与 ACME 当前材料、有限重试信息、全量同步恢复标记以及每个站点一份待确认结果。错误码属于部署结果，TXT 本地状态只保存最近检查和最近成功时间，当前有效性在读取时按固定宽限期推导。前缀读取使用固定大小分页，完整前缀清理使用 etcd 范围删除，使站点数量增加时单次响应仍保持有界。

网站内容位于 sites/，临时下载和展开位于 work/。进程取得数据根目录锁后重建 work/，清理异常退出遗留的半成品；已经确认的不可变内容位于独立站点目录，不受启动清理影响。

收到当前站点后先保存事实，再把仓库 ID 放入有界部署队列。工作线程开始处理时重新读取该仓库的最新事实，因此排队期间发生的摘要、名称或域名变化会自然生效。同一仓库正在部署时再次更新，会在当前任务结束后再处理一次。队列满时，扫描协程在出现空位后继续填充；启动时执行恢复扫描，运行期间每五分钟扫描仍未落实的目标。

部署主动下载当前 TAR.GZ，完成摘要和归档检查后展开为不可变候选，再交给发布器。发布器确认入口后保存安装摘要并清理旧目录；发布器返回错误时恢复旧入口并删除失败候选。embedded etcd 无法保存部署结果时，实例仍直接尝试上报当前失败，使仓库页面能看到本地存储故障。

实现验收点

  • 每个实例运行一个不开放网络端口的内嵌 etcd，同一数据根目录只能由一个进程使用。
  • etcd 前缀按固定页读取，完整前缀使用范围删除，大量站点不会形成无限响应。
  • 启动时重建 work/，异常退出遗留的临时内容得到清理，sites/ 中已确认内容保持不变。
  • 初次同步和当前成品变化都会主动部署，访客请求只读取已确认内容。
  • 队列只保存仓库 ID，执行时读取最新事实；队列满后扫描协程会随空位继续安排。
  • 发布错误保留旧入口和旧内容；没有旧内容时对应地址保持未发布。
  • etcd 写入故障仍会通过现有结果接口报告，恢复扫描继续按最新事实处理。

内置服务与可嵌入发布器

gitea.dev/page 同时提供标准程序和 Go 公共包。page.Run 组装内置 HTTP 服务、同步服务和优雅关闭；自定义 Web 端实现 Publisher 后使用 page.NewService，复用 Gitea 注册、同步、TAR.GZ 检查、业务 TXT 和结果上报。

Publisher.Restore 在启动时以迭代器提供已确认部署，避免为大量站点复制完整切片。Publish 收到仓库 ID、默认地址、可选自定义地址和已经检查的 Content；内容可以通过 Content.Open 读取，也可以取得只读目录接入现有 Web 服务。Publication 分别说明默认地址与自定义地址是否已经实际可用。发布器返回错误表示入口应用失败，并在返回前恢复原有入口；Unpublish 成功后核心再清理内容和保存关闭结果。

同一仓库的发布调用由核心串行，不同仓库按部署并发设置并行。内容目录在下一次成功发布或关闭前保持有效。自定义发布器负责自己的 HTTP、TLS 和入口核验，核心继续负责内容与状态闭环。

标准程序只有一个内置 HTTP 发布器。server.https.mode 用来说明公开 HTTPS 的责任归属：

模式公开地址本机服务和确认方式
disabledHTTPPages 监听 HTTP，并通过该监听器确认网站已生效。
proxyHTTPSPages 只监听 HTTP 源站；前置代理终止 TLS 并保留原始 Host，Pages 通过本机 HTTP 源站确认网站已生效。
pagesHTTPSPages 同时监听 HTTP 和 HTTPS，管理证书与 ACME；已知 Host 的普通 HTTP 请求跳转到 HTTPS，HTTP-01 挑战直接响应。

proxy 模式把外部 TLS、代理健康和转发配置交给部署者，Pages 只确认自己直接控制的 HTTP 源站。这样发布成功表示内容和路由已经在本进程生效，不依赖 Pages 无法可靠观察的代理内部状态。pages 模式的 HTTPS 探测使用本机 HTTPS listener、真实 Host 和证书名称，证书与路由同时可用后才确认地址。

归档只要求至少一个普通文件。内置服务在目录存在 index.html 时按静态网站处理；没有首页时目录请求返回 404，实际文件仍可按完整路径访问。

实现验收点

  • page.Run 可以运行内置 HTTP 服务，自定义程序可以只依赖公开类型实现 Publisher 并运行 Service。
  • 自定义发布器收到的内容已经完成摘要、路径、大小、条目和符号链接检查。
  • 启动恢复使用迭代访问；同一仓库发布串行，不同仓库可以并行。
  • 发布器错误恢复旧入口，成功关闭入口后核心再清理内容。
  • disabled 通过 HTTP 服务和探测，proxy 通过本机 HTTP 源站服务和探测，pages 通过本机 HTTPS 服务和证书探测。
  • proxy 向 Gitea 注册 HTTPS 根地址，同时不启动证书、ACME 或 HTTP-01 处理。
  • 没有 index.html 的有效归档可以发布，实际文件仍可访问。

<custom-root>/index.html
<custom-root>/errors/404.html
<custom-root>/assets/**

启动时检查根目录、常规文件、相对路径、文件数量和总大小。自定义资源最多 1,000 个文件、总计 16 MiB。

数据根目录包含：

<data-root>/etcd/                         内嵌 etcd
<data-root>/sites/<repo-id>/content-*     不可变已检查内容
<data-root>/work/                         下载和展开临时文件
<data-root>/pages.lock                    进程锁

运维证书目录与数据根目录分离，使内容清理不会作用到证书输入。清空数据根目录是本地状态损坏后的恢复入口；下一次启动没有游标，会全部查询并重新部署当前站点。

实现验收点

  • Gitea 启动时校验 [pages] 大小、数量、周期、批量和 DNS 配置，并指出错误字段。
  • [storage.pages] 可以继承通用存储或使用 Gitea 已支持的远程后端，Pages 实例只通过鉴权接口下载内容。
  • 标准程序只通过 --config 读取严格 YAML，未知字段、额外文档和不一致的 HTTPS 模式在启动时返回具体错误。
  • Gitea 地址可以使用 HTTP 或 HTTPS；pages.root_url 与 HTTPS 责任模式保持一致。
  • proxy 只要求 HTTP listener；pages 同时要求 HTTP 和 HTTPS listener，并加载证书配置。
  • Pages 业务 TXT 与 lego DNS-01 可以使用不同解析器，ACME 解析器空值继承业务 TXT 解析器。
  • DNS-01 provider 名称和参数来自 YAML，参数构造结束后恢复进程环境，凭据不会进入 etcd 或 Gitea 上报。
  • 标准构建可在运行时选择 lego provider，轻量构建选择未编入的 provider 时在启动阶段返回错误。
  • 自定义根目录按与内置资源一致的相对路径覆盖首页、404 和 assets，并执行文件数与总大小检查。
  • 数据根目录只有 etcd、站点内容、临时工作和进程锁；清空后自然执行全部查询。

内容目录和归档校验

TAR.GZ 的检查职责和固定资源限制由发布章节统一定义。Pages 下载后重新计算 SHA-256，在临时目录实际解压并检查路径、条目、大小、深度、符号链接和文件系统结果；通过后成为不可变候选，再由发布器决定入口切换。普通文件执行位清除，允许的站点内相对符号链接保留，链接可以解析到站点根目录，目标尚不存在时也可部署；越界、循环、穿过普通文件、硬链接和特殊文件拒绝，符号链接解析最多 32 层。归档至少包含一个普通文件，文件名和目录位置不受首页约定限制。

Gitea 接收和 Pages 展开使用同步的资源边界，默认是压缩后最多 100 MiB、展开后最多 512 MiB、单个文件最多 100 MiB、最多 10,000 个条目。规范化路径最多 1,024 字节、目录深度最多 32 层、符号链接解析最多 32 层属于格式安全规则并保持一致。两端用相同的 UTF-8 相对路径规则和条目类型规则检查，使成品通过管理面后仍能在实例本地安全展开。

实现验收点

  • Pages 只安装摘要匹配且完整检查的 TAR.GZ。
  • 临时展开失败不会替换当前目录，实际磁盘写入失败保留旧内容。
  • 站点内指向未存在目标的相对符号链接可以完成部署，访问时返回网站 404。
  • 解析到站点根目录的相对符号链接可以完成部署；越界、循环、穿过普通文件、硬链接和特殊文件得到明确错误。
  • 当前目录按 repo_id 和成品摘要隔离，同名新仓库不会读取旧目录。
  • 资源边界采用最近同步的 Gitea 配置，路径和符号链接安全规则在两端保持一致。
  • 归档不依赖 index.html；没有首页文件时实际文件仍能按路径访问。

证书、TXT 与故障恢复边界

证书、ACME、挑战和私钥由 Pages 维护；Gitea 只保存业务 TXT 结果、实例地址和最终发布错误。业务 TXT 的两端检查见访问章节，证书细节见证书章节。

Gitea 失联时 Pages 使用最后确认的本机状态继续服务，并在本机维护 TXT、证书和清理工作。结果上报失败时 etcd 保留每个站点一份最新待确认结果；etcd 本身无法写入时直接尝试上报当前失败，并由后续扫描重新确认。收到 state_changed 后按最新站点事实重新部署。状态损坏时停止 Pages，清理 YAML 中 pages.data_root 指定的数据根目录，再重启实例。空数据根目录会使 Pages 以首次同步方式按 Gitea 提供的时间顺序查询全部站点并重新部署；这条运维恢复路径不需要额外的本地版本状态。

实现验收点

  • Gitea 不保存 ACME 订单、证书、私钥或 DNS 凭据。
  • 失联期间已生效网站继续服务，恢复后从本机状态继续同步。
  • 结果上报只有一份待确认内容，旧结果不会覆盖较新的站点事实。
  • 本地状态无法写入时使用现有结果接口直接上报错误，恢复后仍按最新事实重试。
  • 清理数据根目录并重启后从空状态开始，按 Gitea 时间顺序完成全量同步并重新部署。

Gitea Codespace 总体设计

产品边界

Gitea Codespace 为仓库、提交和合并请求提供可停止、恢复和删除的远程开发环境。用户选择运行环境与 Dev Container 配置，Gitea 完成权限确认并建立操作，Manager 再把操作收敛为 Kubernetes 资源和可访问的开发容器。

Gitea 是用户、仓库权限和业务状态的权威来源；Manager 是运行资源的控制面；Dev Container 描述仓库需要的开发环境。明确这三个边界，可以让 Gitea 在不了解 Kubernetes 的情况下完成授权，也让运行平台在不了解 Gitea 内部模型的情况下恢复资源。

实现验收点

  • 分支、标签、提交和合并请求使用同一创建流程。
  • 仓库没有 Dev Container 配置时，用户可以选择可见的命名模板。
  • Gitea 页面、模型和 RPC 不包含 Kubernetes、RuntimeClass 或容器网络字段。

  • 同一操作版本贯穿 Gitea、Codespace 自定义资源和 Agent 任务。
  • Gateway 数据流不经过 Manager 转发。
  • Gateway 只接受与当前 Pod 身份、路由和目标版本匹配的票据。
  • Manager 重启后能从 Gitea 与 Kubernetes 恢复协调状态。

运行原则

每个 Gitea 站点使用独立命名空间。Runtime Pod 在明确选择的 Kata 或 Sysbox RuntimeClass 中运行专属 Docker，实际 Dev Container 由该 Docker 构建和启动。工作区、Docker 数据和 IDE 数据保存在独立 PVC；短期 Token、Secret 和 socket 保存在易失目录。

RuntimeClass 在环境模板中显式选择。Kata 与 Sysbox 具有不同的隔离条件，恢复继续使用创建时确定的配置，从而保持安全边界稳定。环境恢复以 PVC 中的持久数据为准，Cache 只保存可以重新生成的加速数据。

实现验收点

  • 不同站点的资源、凭据和网络策略位于各自命名空间。
  • stop 保留 PVC，resume 使用同一工作区和内部 Docker 数据。
  • Runtime Pod 不获得节点容器运行时套接字或 Kubernetes API 凭据。
  • 清空 Cache 不影响已有 Codespace 从 PVC 恢复。

Gitea 服务端

Gitea 是 Codespace 的业务控制面：它确认用户权限、保存用户可见状态、签发短期凭据，并把运行操作交给 Manager。Kubernetes 实现见运行平台。

用户流程

仓库、提交和合并请求页面提供带当前上下文的创建入口；/-/codespaces 提供跨仓库列表；详情页展示状态、访问入口、资源使用、设置和操作日志。用户设置与站点管理分别维护个人对象和全局对象。

创建先锁定提交并解析 Dev Container，再让用户确认环境、配置来源、附加仓库权限、会注入的 Secret 名称和自动停止设置。环境需要明确选择；Manager 暂时离线时，已经声明的环境仍可用于排队。

创建入口依附仓库上下文，集中列表管理已有环境。这样创建时不重复选择仓库，跨仓库管理也有稳定入口。

实现验收点

  • 分支、标签、提交和合并请求进入同一确认流程。
  • 没有可用环境时页面说明基础设施状态，不创建业务记录。
  • 配置、权限或 Secret 范围变化后需要重新确认。
  • 列表只返回当前用户可见的数据，并支持分页和状态筛选。

权限与身份

Codespace 归创建用户所有。页面、表单和令牌接口都从当前登录身份重新查找对象；URL 中的 ID 或 UUID 只用于定位。创建至少要求主仓库代码读取权限，附加仓库授权取用户当前权限与已确认范围的交集。

Codespace Token 由独立认证方法优先识别。通用 Token scope 与凭据标识通过 Gitea 的 Doer.ExtDoerData 传递，Codespace 仓库授权仍在请求上下文中校验。这样通用权限判断可以沿用 Gitea 的实现，管理员持有的 Codespace Token 也不会获得管理员的完整权限。访问授权范围外的公开仓库时，请求保留 Codespace 用户身份用于审计，同时使用匿名只读的仓库权限。

身份用于说明“谁在请求”，仓库权限用于说明“这次能做什么”。两者分开后，公开仓库读取不会扩大 Token 范围，也不会丢失真实请求者。

权限设置集中读取当前用户的授权、仓库规则和使用数量，关联仓库按批次加载，避免列表增长时逐项往返数据库。撤销后的授权保留展示记录，使用数量归零，修改入口同步关闭；读取失败则报告服务错误，避免把数据库故障误认为授权不存在。

实现验收点

  • 每次读取和修改都重新校验对象、仓库与 Runtime 归属。
  • 用户失去仓库权限后，后续运行凭据同步收窄或停止签发。
  • 附加仓库授权不会扩大用户原有权限。
  • Codespace Token 只按 Codespace 权限模型处理。
  • Token scope 和仓库授权同时生效，管理员身份不会绕过 Token 限制。
  • 公开仓库回退仅允许读取，同时保留真实用户身份。
  • 权限列表保持用户隔离、稳定排序和正确的使用数量；权限收窄或撤销后，列表与实际授权同步变化。

Manager 与调度

用户或站点管理员先创建并命名 Manager，再生成一次性注册 Secret。Gitea 只保存 Secret 摘要；注册完成后，Manager 声明访问地址、SSH 主机指纹和环境标签。

create 以未绑定状态入队。Manager 拉取任务时提交当前可接受的标签和容量，Gitea 按所有权、标签和排队顺序选择候选，并通过条件更新完成唯一领取。Manager 分配 Runtime UUID 并绑定后，resume、stop 和 delete 都返回同一 Manager。

环境标签只决定首次调度。已有环境恢复时使用创建时保存的配置，因此标签变化不会隐式迁移环境。

实现验收点

  • 注册 Secret 只在生成时显示，Gitea 只保存摘要。
  • 并发领取同一操作时只有一个 Manager 成功。
  • 个人 Manager 只能领取其所有者的操作。
  • Runtime UUID 绑定后保持稳定，后续操作不重新调度。

生命周期与可观测性

Gitea 为 create、resume、stop 和 delete 建立带版本的操作。领取、续期、日志、Runtime 信息和最终结果都需要匹配当前 Manager、Runtime 与操作版本。完整转换规则见生命周期。

操作日志按单调字节偏移追加，页面按偏移增量读取。CPU、内存、磁盘、Endpoint 和 ready 信息属于可重建的展示数据；过期时显示暂不可用，不据此推测新的业务状态。

实现验收点

  • 非法状态转换在创建操作前返回明确错误。
  • 续期、日志、Runtime 信息和最终结果只接受当前绑定与版本。
  • 长日志可以分页读取，并保持用户查看历史时的滚动位置。
  • 展示数据过期不会把 running 改为 stopped 或 failed。

凭据、配置与后台任务

Gitea 按用途签发 Git/API Token、一次性 Open Code 和 Gateway 会话授权。Open Code 只保存摘要，并在首次成功兑换时由数据库条件删除。Git SSH 私钥由 Runtime 生成并保存在 PVC，Gitea 只接收公钥；用户 Secret 加密保存，运行时按名称和当前仓库范围请求。

Manager 在 create、resume 或恢复运行材料时请求当前有效内容，并写入 Runtime 易失目录。stop 和 delete 撤销运行期 Token，resume 重新签发。Gitea 配置只表达业务入口、Git 传输、超时和日志策略；集群、镜像、RuntimeClass 与 Cache 由 Manager 管理。

后台任务处理排队超时、操作租约、自动停止、失效凭据和 Manager 状态核对。任务通过数据库条件更新保持幂等，允许多个 Gitea 实例重复扫描。

实现验收点

  • Token 权限不超过用户当前权限与确认范围的交集。
  • 同一 Open Code 并发兑换时只有一次成功。
  • 私钥和 Secret 明文不进入普通读取响应或日志。
  • Gitea 启动不依赖 Manager 在线，页面和配置不出现 Kubernetes 选项。
  • app.example.ini 与代码支持的业务配置保持一致。

运行平台

运行平台由 Manager、Runtime Agent、Gateway 和 Cache 组成。Manager 管理一个逻辑 Kubernetes 集群，Gitea 继续负责用户、权限和业务状态。

控制面与资源

Manager 提供管理 API 和 Kubernetes 控制器。多个 Gitea 站点可以接入同一 Manager；每个 GiteaSite 对应一个 codespace-<site-name> 命名空间，站点的 Codespace CR、PVC、Runtime Pod、配额和网络策略位于其中。

EnvironmentTemplate 定义 RuntimeClass、资源、存储、Git SSH 密钥类型和 Dev Container 附加配置。创建时，Manager 把模板内容和平台镜像摘要写入 Codespace CR，确保已有环境恢复时不受模板或平台升级影响。管理 API 使用 Kubernetes UID 与 resourceVersion 处理对象身份和并发修改，Secret 使用只写接口。

实现验收点

  • Manager 只连接一个 Kubernetes API。
  • 不同站点的资源、凭据、配额和网络策略相互隔离。
  • Manager、Gateway、Cache 和 Runtime 使用同一份摘要固定的平台镜像。
  • 模板或平台升级只影响新环境，管理 API 不返回长期 Secret 明文。

Runtime 与持久数据

Runtime Pod 使用平台镜像，Agent 作为 PID 1 启动专属 Docker、准备工作区、创建 Dev Container、执行生命周期命令并提供访问 RPC。Manager 与 Agent 即使来自同一个平台镜像，也运行在不同 Pod 中；同一镜像用于统一发布和审计，不会合并各自的进程与权限边界。用户镜像运行在该 Docker 中，不直接成为 Kubernetes Pod 容器。

环境模板显式选择 Kata 或 Sysbox RuntimeClass。失败时继续保留原隔离选择，因为自动切换会改变安全边界。仓库配置和命名模板进入同一 Dev Container 解析路径；环境模板可以追加 Web IDE 和标准 Feature。

每个 Codespace 使用独立 PVC 保存工作区、内部 Docker、Git SSH 私钥和 IDE 数据。Token、用户 Secret、Unix socket 与进程状态写入易失目录。Agent 先在 PVC 记录操作阶段和结果，再向 Manager 上报，以便响应丢失后重报结果而不重复副作用。

实现验收点

  • Runtime 不挂载节点容器运行时套接字，也不持有 Kubernetes API 凭据。
  • Kata 与 Sysbox 分别在对应 RuntimeClass 上通过真实启动验证。
  • 所有 Dev Container 来源使用同一解析和执行路径。
  • Pod 替换后工作区、内部 Docker 和 IDE 数据保持一致。
  • ready 只在 Dev Container 与必要访问服务可用后发布。
  • Agent 只能通过内部 RPC 接收操作和发布运行事实。

Gateway 与访问

Gateway 提供 HTTP/WebSocket、SSH 和 SFTP 入口。它从 Manager 获取当前路由，每次建立数据流前复核 Gitea 权限并取得短期 Agent 票据，再通过 mTLS 直连 Agent。Manager 不转发用户数据。

路由快照只包含站点已就绪、绑定有效且 Pod 和访问目标可用的实例。实例处于停止、恢复或尚未获得地址等状态时，只从快照中排除该实例；身份冲突同时记录诊断，实际读取故障仍返回错误。签发票据前实时核对站点、实例、Pod UID 和目标版本，因此缓存中的旧路由不能授权新的连接。

Gateway SSH 主机密钥由 Manager 生成，私钥保存在 Kubernetes Secret 中。轮换时创建新的 Secret 和 Gateway 工作负载，再发布新的公钥指纹。Agent 提供 PTY、命令、SFTP、HTTP Endpoint 和回环端口转发；Dev Container 通过本地 Unix socket 管理 Endpoint。

SSH 命令正常退出时先有界排空输出再发送退出状态；断连时同时关闭 RPC 与本地管道，释放被慢客户端阻塞的读取和写入。完成通知可以重复观察，重复关闭保持幂等。TCP 的输入半关闭仍允许读取剩余响应，避免截断请求完成后的数据。

外部 DNS、TLS 和监听器由 Kubernetes Ingress 或 Gateway API 管理，使应用授权与平台证书分别由对应组件负责。

实现验收点

  • 每个数据流都需要当前有效的用户授权和 Agent 票据。
  • SSH 主机私钥只存在于对应 Secret。
  • 单个实例不可用不影响其他实例的路由，Pod 被替换或目标失效后不能获得访问票据。
  • SSH 正常退出保留输出和退出码；断连释放阻塞任务，TCP 半关闭后仍可接收响应。
  • 每张票据只绑定一种访问能力。
  • 本地端口转发只访问当前 Dev Container 的回环地址。
  • Pod 或目标版本变化后，旧路由和票据失效。

Cache

Cache 是独立组件，支持本地文件系统或 S3。它为允许的上游镜像提供代理，并按站点、仓库和用户隔离构建缓存。Runtime 的 Docker 数据保存在 PVC，Cache 只减少重复下载与构建。

Cache 从 Manager 获取配置、短期认证和维护许可。缓存丢失时允许在原授权范围内回源；维护许可保证同一存储同一时刻只有一个垃圾回收执行者。

申请清理许可和提交清理完成均等待 Manager 按请求序号确认。等待受超时和调用取消控制，结束后释放请求记录；迟到的响应只对应原请求，连接故障同时结束尚未确认的维护请求。这样“已发送”与“已完成”有明确区别，重连也不会继续持有旧请求的等待资源。

实现验收点

  • 私有镜像和构建缓存按站点、仓库与用户范围隔离读取。
  • Registry 与仓库组合不会产生缓存键冲突。
  • 清理完成在 Manager 确认后才返回成功；取消、超时和控制流关闭均结束等待，并可在后续有效连接上继续维护。
  • Cache 清空后可以回源，已有 Codespace 仍可从 PVC 恢复。
  • 同一存储同一时刻只有一个垃圾回收执行者。

高可用与恢复

Manager 多副本通过 Kubernetes Lease 选举。只有 Leader 连接 Gitea、领取操作、协调 Runtime 和签发访问票据；备用副本保持可接替状态。新 Leader 先核对 Gitea 当前操作与 CR、PVC、Pod 和 Agent，再领取新任务。

恢复不依赖节点本地文件。Kubernetes 无法证明旧 Pod 已停止写入 PVC 时，Manager 撤销其执行权和路由并保留数据，等待管理员针对当前资源身份确认，再把环境收敛到 stopped，通过普通 resume 启动新 Pod。

实现验收点

  • 同一时刻只有 Leader 推进生命周期操作。
  • 新 Leader 完成资源核对前不领取新 create。
  • 部分清单、未知归属或失联节点不会触发误删或双写。
  • 管理员确认只对当前 CR 和 Pod 身份生效。

生命周期

Gitea 保存用户可见的主状态和当前操作，Manager 负责让 Kubernetes 资源收敛，Agent 负责 Runtime 内的执行。操作版本贯穿三者，使网络重试、进程重启和 Leader 切换不会产生第二条执行链。

状态与操作

主状态含义有操作时的类型
creating已确认创建，环境尚未可用create
runningRuntime 已就绪stop
stopped持久数据保留，Runtime 已停止resume
deleting正在确认平台资源清理delete
failedcreate 已确定无法完成无；允许 delete

操作创建时间大于零表示存在操作；开始时间为零表示 queued，否则表示 running。操作完成后写入新的主状态并清空触发来源和操作时间。操作类型与阶段由主状态和时间唯一推导，不在数据库中保存第二份相同事实。

每个新意图增加操作版本。续期、日志、Runtime 绑定、状态报告和最终提交都需要匹配 Codespace、Manager、操作类型与版本。数据库写入同时比较读取时的主状态、操作版本和操作阶段，只有仍为当前状态时才生效。delete 可以用更高版本替代进行中的 create、resume 或 stop，因为它代表用户的最终清理意图；其他冲突操作返回当前状态。

用户活动代数独立保护活动递增和自动停止取消，Manager 的操作完成则只比较生命周期快照。这样打开 Endpoint 与 stop 完成并发发生时，活动请求保持环境的既定主状态，stop 也保留已经记录的活动代数。

实现验收点

  • 一个 Codespace 同时最多有一个有效操作。
  • 同一持久行能够唯一推导操作类型和 queued/running 阶段。
  • 日志、Runtime 信息和最终结果只接受当前操作版本。
  • 并发状态写入只有一个能够匹配读取时的生命周期快照。
  • 用户活动递增和 Manager 操作完成分别按各自的条件更新生效。
  • 重复提交相同意图保持幂等，不增加操作版本。

Gitea 先锁定目标提交，再在同一数据库事务中校验用户、仓库、环境标签、Dev Container 配置和授权，并创建 Codespace 与 queued 操作。Manager 领取后分配 Runtime UUID，绑定成功后才创建集群资源。Agent 完成工作区、Dev Container 和访问服务初始化后发布 ready，Manager 再提交 create 结果。

输入和权限错误在持久化前返回。确定性执行错误进入 failed；可能已经创建的平台资源继续由同一 Runtime UUID 清理，避免重试生成另一套资源。

实现验收点

  • 创建确认、授权和任务入队位于同一数据库事务。
  • 同一 create 只对应一个 Runtime UUID、一组 CR/PVC 和一个有效操作版本。
  • Runtime UUID 绑定前不创建对外可用的 Runtime。
  • 页面在 create 完成前可以按偏移读取日志，成功后状态为 running。

运行与访问

running 状态下，Agent 向 Manager 发布当前 Pod 身份、访问目标和 Endpoint；Gateway 在每次连接前复核 Gitea 权限并取得短期票据。用户活动更新最后活动时间，用于自动停止；组件心跳和后台状态检查不计为用户活动。

Runtime 信息是可重建的展示数据。暂时失联会让访问入口显示不可用，但不会把 running 推测为 stopped 或 failed。

实现验收点

  • 私有 Endpoint、Web IDE、SSH 和 SFTP 均需要当前用户授权。
  • 公共 Endpoint 仍需匹配当前 Runtime 和 Endpoint 声明。
  • 后台心跳不会延后自动停止。
  • Runtime 信息过期不改变主状态。

停止、恢复与自动停止

stop 定向到已绑定 Manager。Manager 撤销路由和运行期凭据、停止 Runtime Pod 并保留 CR/PVC，确认完成后 Gitea 进入 stopped。resume 复用 Runtime UUID、CR、PVC 和已确定的环境配置，创建具有新 Pod UID、Agent 身份和访问目标版本的 Pod。

首次创建由 init 后进入 start；恢复只执行同一 start 语义。环境标签用于首次调度，后续改名或删除不会迁移已有 Codespace。自动停止通过普通 stop 操作实现，因此具有相同版本、清理和恢复行为。

Manager 通过活动代数判断自动停止设置的新旧，设置同步与自动停止响应采用同一更新规则。较新的用户活动会重新开始空闲观察；重复收到相同设置保留已有空闲计时，延迟到达的旧设置也不会覆盖较新的活动，保证网络重试不改变用户的空闲期限。

实现验收点

  • stop 后持久数据保留，Runtime Pod、路由和运行期 Token 消失。
  • resume 不重新克隆仓库，也不重放初始化或一次性生命周期命令。
  • resume 发布新的 Pod 身份、访问目标版本和短期凭据。
  • 手动停止与自动停止使用同一状态转换，并发扫描不会创建重复操作。
  • 设置更新和自动停止响应均保留较新的活动代数；重复设置保留空闲计时，新的活动重新开始观察。

删除

delete 生效后，只有当前 delete 版本可以发布状态。Manager 依次撤销访问、停止执行并删除 Pod、PVC、CR 和路由信息；确认平台资源消失后，Gitea 清理业务关系、凭据、日志和展示数据。

删除步骤以资源身份和稳定名称保持幂等。资源已经不存在表示该步骤完成；资源状态尚未确认时保持 deleting，并由后续协调继续核对。

实现验收点

  • create、resume 或 stop 期间发起 delete 最终能够收敛。
  • 重复 delete 不会重建资源，也不会因资源已经不存在而失败。
  • deleting 只接受当前 delete 版本的操作结果。
  • 平台资源确认清理前，业务状态保持可诊断。

超时与恢复

create 和 resume 的排队或执行期限用于结束无法启动的请求：create 进入 failed，resume 回到 stopped。stop 和 delete 表达必须完成的收敛意图；执行许可到期后以更高操作版本重新排队，并保留首次创建时间用于诊断。

Manager Leader 接管时先续期仍绑定的操作，再提交完整资源清单并核对 Gitea、CR、PVC、Pod 和 Agent。已成功且持久记录的 Agent 阶段只重复上报结果；开始后未记录完成的阶段明确失败，因为盲目重放可能重复修改用户环境。旧 Pod 是否仍可能写入 PVC 的处理见运行平台。

操作续租与结果、Metadata 上报使用独立循环，避免慢上报占用续租时间。上报循环先通过本地资源缓存判断是否到达刷新周期或存在待确认结果，实际执行时再读取实时站点、凭据和资源列表。Watch 合并有关配置、身份、目标和结果的变化；单纯的上报代数与启动进度由定期刷新处理，减少无意义的实时读取和路由重建。

实现验收点

  • create/resume 超时进入明确稳定状态，stop/delete 超时继续收敛。
  • 两个 Manager 竞争时只有一个能领取同一操作。
  • 新 Leader 不依赖前任进程内状态即可恢复协调。
  • 已完成阶段不会重放，结果未知的阶段提供明确诊断。
  • 空闲上报检查只读取本地缓存；有待上报内容时仍以实时身份和资源状态为准，慢上报不阻塞续租。

数据模型

本文定义数据归属、稳定标识和持久化不变量。列名、索引和自定义资源字段以模型、数据库迁移和 CRD 为准。

数据归属

数据层权威内容恢复方式
Gitea 数据库所有权、仓库提交、授权、业务状态、操作和 Manager 绑定从数据库恢复
Kubernetes API站点、环境模板、运行意图和资源状态由 Manager 控制器重新核对
Codespace PVC工作区、Git 私钥、内部 Docker 和 IDE 数据由新的 Runtime Pod 重新挂载
组件内存连接、Leader 工作集和短期授权缓存从权威来源重建

每项持久事实只有一个权威来源。展示缓存过期只影响信息是否可见，不改变业务状态。这样恢复过程只需核对权威数据，不需要比较多个副本的更新时间。

实现验收点

  • 每项持久数据都能指出唯一权威来源。
  • Manager 丢失进程内状态后能从 Gitea 与 Kubernetes 恢复。
  • Gitea 不访问 Kubernetes API 也能执行权限判断和展示业务状态。
  • Pod 重建不会丢失 PVC 中的用户数据。

Gitea 业务数据

Gitea 保存 Codespace、Manager、Dev Container 模板、运行期凭据、用户 Secret 和附加仓库授权。全局对象与个人对象通过所有者区分，并由查询和数据库约束共同限制可见范围。

Codespace 保存恢复业务状态所需的确定输入：所有者、仓库与锁定提交、环境、当前状态、操作版本、Manager 与 Runtime 绑定，以及确认后的 Dev Container 来源。仓库配置引用锁定提交中的路径；命名模板保存创建时选定的正文，之后修改模板只影响新环境。

Runtime UUID 在 Manager 领取前为空，绑定后全局唯一。用户 Secret 加密保存，列表只返回名称与适用范围。Open Code 只保存摘要、目标和过期时间，并由数据库事务一次消费。运行材料按当前权限签发，不作为 Codespace 快照长期保存。

实现验收点

  • 多个未领取的 Codespace 可以同时排队，每个已绑定 Runtime UUID 只对应一个 Codespace。
  • 创建失败不会留下半条 Codespace、孤立授权或明文凭据。
  • 模板修改不会改变已有 Codespace 的恢复输入。
  • Secret、Open Code 和运行期 Token 的明文不会出现在列表、日志或普通读取接口中。

平台数据

GiteaSite 和 EnvironmentTemplate 是集群级资源；Codespace CR 位于站点命名空间。CR Spec 保存平台执行所需的固定输入和当前操作，Status 保存控制器观察结果。用户 Secret 和 Gitea Token 通过短期投递进入 Runtime，不写入 CR、标签或注解。

PVC 是环境数据的持久边界。stop 删除运行工作负载并保留 PVC，delete 确认清理后才回收 PVC。Cache 保存可重新生成的性能数据，不属于业务备份。

实现验收点

  • 不同站点的 Codespace 资源位于不同命名空间。
  • CR Spec 表达期望，Status 表达观察结果，两者均不保存业务 Secret。
  • 删除 Pod 不会删除 PVC，完成 delete 后不遗留 Codespace 持久资源。
  • Cache 丢失后可以回源，不影响 PVC 中的环境数据。

标识、并发与清理

Gitea ID 表示业务关系，Runtime UUID 表示跨站点运行身份，操作版本区分连续用户意图，Kubernetes UID 区分同名资源实例，目标版本区分 Agent 的连续发布。跨站点查找 Runtime 时同时使用站点身份和 Runtime UUID。

创建事务原子保存 Codespace、初始操作和用户确认的授权。领取、完成、超时与恢复通过读取时的状态、操作版本和绑定关系进行条件更新；更新不到记录表示其他请求已经推进状态。用户活动代数独立保护活动更新和自动停止取消，因此用户活动与 Manager 操作结果可以各自收敛。

日志按操作版本和单调偏移追加。指标、Endpoint 和 ready 信息属于可重建展示数据。delete 完成后清理业务关系、运行凭据、日志和展示数据。

实现验收点

  • 状态写入只接受当前操作版本、Pod 身份和目标版本。
  • 并发领取和完成依靠数据库条件更新与唯一约束只产生一个结果。
  • 日志只由当前操作按单调偏移追加。
  • 展示数据过期不触发主状态转换。
  • delete 完成后旧 Token、Open Code 和日志不可继续使用。

RPC 接口

本文定义跨进程职责、安全边界和重试语义。Gitea 与 Manager 的公共接口以 codespace-proto-go 为准；Manager、Agent、Gateway、Cache 与 Runtime 命令之间的接口由 codespace/internal/rpc 维护。两类接口分别归属跨仓库业务边界和 Codespace 内部运行边界，因此可以独立演进。

Gitea 接口只表达 Codespace 业务语义；Kubernetes、Pod 和缓存后端留在 Manager 与内部协议。平台使用同一个二进制交付各组件，但 Manager、Agent、Gateway、Cache 和 Runtime 命令运行在不同进程或 Pod 中，仍需要明确的进程间通信。生成代码和调用端统一使用 Connect v2，通过 HTTP 传输适配器承载 Connect/gRPC，复用双向流、取消、背压、消息限制和 mTLS，避免维护额外的自定义传输格式。身份从请求元数据传入认证上下文，协议版本在接收消息时校验，业务方法直接接收和返回 Proto 消息。

实现验收点

  • 每个请求都能从认证上下文和消息确定调用者与目标。
  • 未知协议版本返回明确错误，不进入业务处理。
  • Gitea 协议不包含 Kubernetes 调度或容器网络配置。
  • Gitea 与 Codespace 使用同一已发布协议版本。
  • 公共协议模块只生成 codespace/v1，内部协议只能由 Codespace 导入。

Gitea 控制面

Manager 声明自身、领取和完成操作，上报日志、Runtime 信息与资源清单，并按需请求运行材料。所有操作请求携带当前版本；Runtime 报告同时绑定 Manager 和 Runtime 身份。Runtime UUID 由 Manager 在领取 create 后生成，Gitea 通过数据库唯一约束完成一次绑定。

没有任务的轮询返回正常空结果。高频成功轮询可以省略普通 HTTP 请求日志，错误仍保留诊断信息。

ManagerService 的请求和响应统一限制为 32 MiB，两端直接使用公共协议包中的常量。传输限制与 Kubernetes 单个持久化对象的大小限制分别生效：前者容纳资源清单等批量消息，后者控制资源保存成本。

实现验收点

  • Manager 凭据只能操作对应的 Manager 记录。
  • 领取、续期、日志、Runtime 报告和完成都校验当前绑定与版本。
  • 每个 Runtime UUID 只绑定一个 Codespace，未绑定请求可以正常排队。
  • 运行材料按请求时的用户和仓库权限生成。
  • 两端接受相同大小范围的 RPC 消息，资源保存仍执行自己的对象大小校验。

组件与 Agent

Gateway 和 Cache 使用各自身份连接 Manager，并接收版本化配置；发现版本缺口时重新获取完整快照。Gateway 建立用户流前请求业务授权和短期 Agent 票据。Cache 按配置限制上游、缓存范围和维护动作。

Agent 以当前 Codespace CR 和 Pod 身份建立控制流。生命周期命令绑定操作版本，日志使用独立流，避免大量输出阻塞控制命令。Agent 先把阶段和结果原子写入 PVC，再向 Manager 上报，重连时复用已经完成的结果。

Gateway 使用按能力签发的短期票据访问 PTY、SFTP、HTTP Endpoint 或回环端口。Dev Container 通过挂载的 Unix socket 管理 Endpoint，不需要访问 Manager 网络端口。

内部 Proto 生成到 codespace/internal/rpc，从 Go 包边界上阻止其他仓库依赖运行实现。需要跨越 Gitea 与 Manager 的业务类型由公共协议定义，内部协议直接引用这些类型，避免维护重复消息。

实现验收点

  • Gateway 与 Cache 分别使用绑定自身角色的身份和能力。
  • 控制流重连后可以从完整快照恢复配置。
  • 控制流建立失败和运行中断都进入现有重连流程，取消请求会释放连接。
  • Agent 票据只适用于一个 Runtime、Pod、目标版本和访问能力。
  • 日志背压不会阻止控制命令。
  • Dev Container 可以通过本地 socket 增删和查询 Endpoint。
  • 公共业务类型在公共协议中只有一份定义。

错误、重试与关闭

接口使用标准 RPC 状态区分参数、认证、权限、对象、状态冲突和暂时不可用。写操作通过操作版本、资源 UID、Metadata 代数或稳定资源键实现幂等。

请求校验错误明确标记为参数错误，已知业务冲突映射到对应状态。数据库、缓存和其他未分类内部故障返回脱敏的 Internal，服务端记录诊断原因；取消和超时保留各自的状态。FailureDetail 只携带调用端实际使用的分类，代数和日志偏移的一致性由服务端校验以及成功响应共同保证。

所有跨组件连接都具有应用层身份。流式接口限制消息大小、空闲时间和缓冲；组件关闭时先停止接收新请求，再在有限时间内释放已有连接。

实现验收点

  • 同类失败在不同服务中使用一致的 RPC 状态。
  • 客户端错误不暴露内部查询和目标地址，错误与诊断日志均不输出 Token、Secret 或私钥。
  • 网络重试不会创建第二个操作、Runtime 或命令执行。
  • 慢客户端和关闭中的连接不会无限占用资源。

部署要求

本文面向集群管理员，说明上线所需的平台能力和验收场景。安装命令与 values 由 Helm chart README 维护。

Kubernetes 基础能力

Manager 连接一个逻辑 Kubernetes 集群。集群需要提供 CRD、Lease、PVC、NetworkPolicy、RuntimeClass、Service，以及入口使用的 Ingress 或 Gateway API。Helm chart 安装 CRD、RBAC、Manager、内部服务、管理服务和网络策略。

管理服务默认为 ClusterIP，首次配置通过 kubectl port-forward 完成。Manager 多副本使用 Lease 选举；健康副本保持 Ready，内部 RPC 与管理服务只选择当前 Leader。Ready 表示副本可以参与接替，Leader 标签表示副本可以处理有状态请求，这两个信号分别服务可用性和单写者约束。

实现验收点

  • 启动检查能指出缺失的 API、CRD 或 RBAC 权限。
  • 默认安装只提供集群内管理入口，端口转发可以完成首次配置。
  • 内部 RPC 与管理服务只把流量发送给当前 Leader。
  • Leader 和 Cache 维护 Lease 位于管理命名空间。

隔离、存储与设备

每个环境模板绑定经过验证的 RuntimeClass、StorageClass、资源限制和 Dev Container 附加配置。Kata 需要硬件虚拟化或可用的嵌套虚拟化；Sysbox 需要受支持的内核、容器运行时和存储驱动。设备通过 Kubernetes 扩展资源和设备插件分配。

Kata 与 Sysbox 分别按官方文档安装，并先在专用节点池使用平台镜像和目标 StorageClass 完成真实 Pod 验证。每个 Codespace 使用独立 PVC，StorageClass 需要适配所选 RuntimeClass、节点和扩容策略。

实现验收点

  • 每个启用模板都有 RuntimeClass、StorageClass 和平台镜像的真实验证记录。
  • Runtime 内 Docker 可用，并且无法访问节点容器运行时或 Kubernetes API 身份。
  • CPU、内存、磁盘和设备使用受模板限制。
  • Pod 替换后 PVC 数据可以由新的 Runtime 恢复。

镜像、缓存与网络

Manager、Gateway、Cache 和 Runtime 使用同一个摘要固定的平台镜像，但作为独立工作负载运行。私有仓库凭据通过 Helm 引用现有 Docker Registry Secret；Manager 只向需要拉取镜像的站点命名空间同步凭据。

Dev Container 镜像由 Runtime 内的 Docker 拉取或构建。Cache 可以使用 PVC 或 S3，内容属于可重新生成的性能数据。每个站点使用独立命名空间和 NetworkPolicy；用户流量统一进入 Gateway，再由 Gateway 连接 Agent。外部 DNS、TLS 和监听器由集群入口管理。

实现验收点

  • 部署镜像与 Manager 固定的工作负载镜像使用同一摘要。
  • 私有仓库凭据只投递给需要它的工作负载。
  • Runtime 无法访问其他站点的 Runtime 网络。
  • HTTP、WebSocket、SSH 和 SFTP 用户流量均经过 Gateway。
  • Cache 清空后可以在原授权范围内回源。

身份、容量与恢复

Manager 和组件身份由 cert-manager 签发。管理员令牌、Gitea 注册 Secret、组件身份、Gateway SSH 主机密钥、对象存储凭据和镜像凭据通过 Kubernetes Secret 投递并纳入轮换。

环境模板定义单个 Runtime 的资源请求，Gitea 站点定义总配额。Manager 统计实际资源和正在创建的任务，Kubernetes 调度器负责节点放置。备份覆盖 Gitea 数据库和日志、Kubernetes 管理资源、Codespace PVC 以及恢复所需的 Secret。

升级先更新 CRD，再更新平台组件。新环境使用新镜像摘要；已有环境使用创建时保存的摘要，因此镜像仓库需要保留仍被引用的版本。

实现验收点

  • Secret 不出现在 ConfigMap、CR、标签或普通日志中。
  • 凭据轮换后旧身份和旧会话按有效期失效。
  • 站点配额包含运行中和正在创建的 Runtime。
  • 恢复后站点、Runtime UUID、PVC 与 Gitea 记录能够重新关联。

上线验收

正式启用前应在目标集群完成：

  1. 两个站点分别完成创建和删除，验证资源与网络隔离；
  2. 每种启用的 RuntimeClass 完成 create、stop、resume 和 delete；
  3. 验证 Web IDE、PTY、SSH、SFTP、HTTP Endpoint 与回环端口转发；
  4. 替换 Runtime Pod，验证旧访问失效和 PVC 数据恢复；
  5. 切换 Manager Leader，验证操作保持唯一执行；
  6. 清空 Cache，验证授权回源；
  7. 审计 RBAC、NetworkPolicy、Secret 和测试资源清理结果。

实现验收点

  • 验收记录包含组件版本、RuntimeClass、StorageClass、镜像摘要和结果。
  • 失败能够从页面与日志定位到具体阶段。
  • 写入者停止确认绑定当前 CR 与 Pod 身份。
  • 验收结束后没有孤立的 CR、PVC、Pod、凭据或路由。

实施与测试

本文面向贡献者，说明代码归属、验证层次和完成标准。业务行为由其他设计章节定义。

仓库与代码边界

仓库职责
gitea业务模型、权限、页面、Manager RPC 和后台任务
codespace-proto-goGitea 与 Manager 的公共 Proto 和生成代码

公共协议先在 Proto 仓库修改、生成、测试并发布，再更新两个实现仓库的远程依赖。Codespace 内部协议随实现一起生成和测试，并从固定的公共协议依赖读取共享业务类型。Gitea 的业务规则放在 model/service，router 负责请求与响应；Codespace 按控制面、Runtime、Gateway、Cache、Dev Container 和管理界面组织。

逻辑优先留在拥有该行为的领域。只有多个流程共享同一不变量时才提取接口或公共包，以免单次调用的小函数和空抽象分散主要流程。

实现验收点

  • 每项功能有唯一仓库和领域归属。
  • Router/Handler 不重复实现状态机、权限或事务。
  • 公共与内部 Proto 均可重复生成，Gitea 与 Codespace 使用已发布的公共模块。
  • Gitea 不导入 Agent、Gateway 或 Cache 的内部协议包。
  • 接口对应真实替换边界，较长流程按稳定业务阶段组织。

测试层次

层次覆盖重点

数据库测试事务、条件更新、唯一约束和迁移
组件集成测试RPC 身份、操作领取、Agent 流、Gateway 授权和 Cache 维护
Kubernetes 端到端测试CR、PVC、Pod、Leader 切换、RuntimeClass、网络和恢复

Helm 测试RBAC、身份、服务、网络策略和摘要固定镜像

测试选择能覆盖风险的最低层次，并通过生产入口验证用户可观察行为。Gitea 使用其 Makefile 和测试文档规定的入口。Codespace 对外提供三个测试入口：make test 运行完整的非端到端测试，make test-smoke 快速验证主要后端包，make test-e2e 编排真实 Kubernetes 全链路。统一入口使本地和自动化执行相同阶段，也避免各子系统各自维护一套环境变量、资源和清理脚本。

实现验收点

  • 状态机覆盖成功、并发抢占、非当前版本和恢复路径。
  • 权限测试覆盖对象 ID 篡改、跨用户、跨站点和凭据重放。
  • 前端测试在项目支持的浏览器中稳定，不依赖精确计时。
  • 本地和自动化使用相同的公开测试入口。
  • 普通测试不会因为本机存在 kubeconfig 或 Docker 而隐式进入真实环境测试。
  • 完整端到端测试由单个入口启动，阶段失败会直接终止并保留诊断。

真实环境验证

Kubernetes 端到端测试在专用测试集群中使用摘要固定的平台镜像和独立命名空间。一个集群由同一套 Manager 控制面协调集群级 GiteaSite 和 EnvironmentTemplate；独立命名空间用于组织测试资源，其他 Manager 安装需要在测试前停用，以避免两套控制面修改同一资源。Kata 与 Sysbox 通过同一入口分别执行，使结果明确对应实际 RuntimeClass 与 StorageClass。测试在 Runtime Pod 内验证 Docker、Dev Container 和持久卷，而不是借用开发机的容器运行时。

测试开始前检查集群能力、镜像和真实 Gitea 凭据，随后覆盖组件身份、Leader 切换、访问路径、S3 兼容缓存和完整生命周期。成功执行清理测试资源；失败执行先保留 Kubernetes 资源、事件和组件日志，便于定位后再清理。

实现验收点

  • 测试开始前检查集群 API、RuntimeClass、StorageClass、镜像和凭据。
  • 测试集群在执行期间由本轮测试安装的 Manager 控制面协调。
  • 每种支持的隔离模式完成 create、stop、resume、delete 和访问验证。
  • Leader 切换、Pod 删除与 Cache 丢失具有恢复验证。
  • Runtime Pod 内完成 Docker 数据恢复和 Dev Container 官方场景验证。
  • S3 Cache 使用隔离的 S3 兼容服务完成写入、读取和清理验证。
  • 真实 Gitea 凭据只从文件读取，不出现在测试命令参数和日志中。
  • 测试结束后自动确认没有孤立资源。

完成标准

一次变更完成时，设计、协议、实现、配置与测试需要描述同一当前行为。格式化、静态检查、适用测试和安全边界验证使用仓库公开入口执行；真实环境中未执行的部分在变更说明中记录原因与风险。

实现验收点

  • 审阅者可以从设计验收点定位对应代码和测试。
  • 配置示例、管理页面和部署清单随实现更新。
  • 工作树没有意外生成物，测试资源和临时凭据已经清理。
  • 变更说明列出已执行测试及尚未验证的真实环境场景。
